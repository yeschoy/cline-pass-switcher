# Design: bounded scheduled account-scoped channel checks

> Planning draft, not permission to deploy or call the real upstream. Source boundaries: `server.js:2616-2785,3827-3859,4033-4131,4499-4671,5510-5525,5589-5618`; backend persistence/routing/client-key specs and frontend state/quality specs.

## Product semantics fixed in planning

Default enabled; 5-minute **scheduler tick**, not a promise to check every channel every 5 minutes. Each tick starts at most two real chat calls; across a rolling 24 hours all automated checks collectively have at most 100 calls (both limits configurable). Only known channels of subscribed models are eligible, never automatic catalog discovery. Recently used `(account ID, resolved model, configured-or-discovered channel)` triples receive priority, with a reserved portion of the budget for low-frequency triples. A triple's 3 consecutive **separate-round, reliable channel-specific failures** causes that account alone to avoid it; unknown/local/account/proxy outcomes do not increment the streak. One later reliable success or an explicit administrator recovery clears the hold. The hold has **no time-based release** and survives restart; status must show the age of evidence. If the currently selected account's only remaining permitted candidates are held **solely** by these automatic probe holds, it may try exactly one candidate according to the pre-existing safe order, no second held-channel retry or account replacement from that failed exploratory attempt. Hard quarantine, durable cooldown and manual `exclude` always retain precedence and can still produce the existing safe `503`.

## Owners and persisted contracts (proposal for review)

- Reuse `server.js` as the sole scheduler/validation/config/metadata owner. Extend the existing `scheduleQuotaRefresh()` timer and shutdown coordinator to dispatch a *nonblocking bounded provider-check slice* when due. Do not create a second queue, unbounded Promise fan-out, or independent timer. Quota work retains its current two-slot admission and cadence; provider checks have their own maximum two in-flight real calls, but reuse `tryLeaseResult()`/`lease.takeRpmPermit()` and account-bound `accountFetchJSON()`/native transport so chat capacity and local RPM remain authoritative. Scheduler work never runs on `handleChat()`'s request path. Start the first automatic tick no earlier than five minutes after listen, with deterministic bounded jitter on restart; no startup catch-up burst.
- A new canonical top-level config object (tentative name `providerProbeSchedule`) contains exact `enabled`, `intervalMs` (default 300000), `maxPerRound` (2), `maxPer24h` (100) and `failureThreshold` (3). Use bounded integer validation on admin writes, conservative startup normalization/migration, same-directory atomic config write, old-client field omission preservation, and an explicit disable path. An admin GET/POST surface for just these values and a read-only bounded status projection avoids reconstructing complete account objects in the UI. Manual `/api/probe` and `/api/validate-upstreams` keep their legacy request and response shapes.
- Persist only bounded safe facts in the existing `metadata.json`: `accountId/model/provider → {streak, held, checkedAt, lastReliableAt, outcome, evidence, lastRound}` plus a bounded rolling budget list/cursor. No account key, proxy URL, Header value, raw body, session/fingerprint or unbounded error note. Strictly validate existing operator data at startup; corrupted/unreadable JSON stops without rewriting. On account deletion/key/proxy/owner rotation, route/model removal or model unsubscription, invalidate obsolete triples and fence late results. **Reviewed identity correction:** mtime alone is not a revision. Generate a private random MAC key in `config.json` (not metadata/API/logs), then bind the persisted probe verdict set to a domain-separated keyed digest of canonical identity-bearing configuration: upstream base, subscribed models, global complete routes and each account's ID/owner/upstream credential/proxy/custom Headers/enablement/complete routes. Compare at startup and after config writes; a mismatched digest clears only verdict cells, never the paid-call budget. An old mtime-only probe schema has no trustworthy identity proof: validate it, migrate with its budget intact and discard verdicts once. Missing or malformed MAC key handling must not silently replace corrupt operator data; generate only for legacy absence using the existing atomic config write path. Do not project MAC key or derived digest in management/status APIs. Test preserved-mtime external edits and restored backups with changed identity, old-schema migration, failed writes, and unrelated admin saves that must not erase valid holds.
- A rolling-24h budget reservation is atomically persisted **before** a possible native send; failure to persist means skip automatic probe and release any reserved permit/lease, never fail model traffic. The ephemeral selected batch may have up to `maxPerRound` candidates, but **at most two** native scheduled checks may be in flight at any moment even when that setting is 10; use two bounded workers over this one batch, not an additional scheduler/queue. Conservatively debit a pre-send attempt rather than risk exceeding the cap after a crash; diagnostics distinguish budget reservation from a committed upstream call. Each actual native chat call takes one existing account RPM permit; manual probes retain their own current behavior and account RPM accounting, and are not silently counted toward the automatic-only daily cap. The daily cap is per server data directory/process, not a distributed multi-replica hard budget.
- **Reviewed capacity policy:** The 5,000-cell persisted evidence bound protects durable holds indefinitely. For a new eligible triple when full, evict the oldest **non-held** cell only (prefer unknown/zero-streak over a partial reliable failure streak); never evict a held cell merely due to age or pressure. Reserve its evidence slot **before** any paid-call debit/native send, transactionally with the existing budget write, so two in-flight calls cannot both spend against one available slot and later drop one result. A pre-send reservation is only unknown/pending, not evidence of success or channel failure; crash/restart must keep the budget debit while treating unfinished evidence as unknown. If all 5,000 cells are held, a new triple has no safe slot: skip it without leasing/RPM debit/paid call/budget debit, but keep existing held triples eligible for budgeted recovery checks. The authenticated status and UI must distinguish candidate coverage from real attempts and record `capacitySkipped`/`storageSaturated` (or equivalent bounded facts) without leaking keys. This is the operator-approved limit: with finite storage and indefinite holds, eventual coverage of every >5,000 eligible triple cannot be promised when all slots remain held. A manual exact recovery or account/route invalidation may free capacity; no time-based hold expiry is added.

## Eligible work, evidence, and routing gate

Build a deterministic, bounded snapshot of configured enabled accounts, subscribed model IDs and each account's effective complete route (`resolveModelConfig()`, `buildProviderPlan()` source, not a global route merge). Known channels may come from that route's configured list or the model's discovered list; remove manual excludes/hard-quarantined providers before scheduling, **but keep auto-held channels in the probing queue for recovery**. Reject credential-less/disabled/hard-banned accounts; owner ID of the account scopes the result, with no cross-owner fallback. Derive recent priority from already bounded safe request history/attempt projections, not original messages or a second persisted per-session store. Reserve a stable low-frequency share (design default 20%) and round-robin cursor so busy triples cannot permanently starve the rest; when either tier is empty, use its available capacity for the other. Rotate the **account start** and model start before the 5,000-cell candidate snapshot truncation (not merely the selected index inside an already truncated list); even if one account alone can fill the snapshot, another eligible account must enter a later round. Use the existing bounded `round` and `cursor` facts in the same metadata owner for **independent** progress: candidate-window rotation must not be canceled by the hot/cold pool pick index. For a complete (<5,000) snapshot, keep a stable candidate order and advance the hot and reserved-cold selection ordinal on each opportunity (a once-per-five-round cold slot must not step over a pool of five forever). For a truncated snapshot, advance its account/model/provider start independently of the within-window pick and prove that every finite eligible tier eventually enters and is selected; do not create a second scheduler/queue/store or a high-cardinality per-triple cursor. Test the two-account and two-model single-slot counterexample, multiple cold candidates with a one-in-five budget share, hot/cold mixture, and >5,000 candidates. A fixed budget ceiling can delay coverage, and full held storage can halt unseen combinations without charging them, so test fairness with sufficient fresh budget **and an evidence slot** across rounds rather than promising a five-minute per-channel interval. Publish coverage (`eligible`, `sampled`, `deferred`, next due, budget remaining) without implying each channel was checked in every 5-minute tick.

Factor a single per-channel validation-result/classification seam from existing `validateUpstreams()`. The manual endpoint keeps writing its existing compatibility status; the automatic path stores **account-scoped** evidence only, never writes a global Provider health sample or account rule action. Preserve `unknown` for local RPM/concurrency, proxy/network/auth/quota faults, malformed response and ambiguous gateway errors; a 16-token `empty response content` is not sufficient to *recover* a held Provider without stronger pin/actual evidence. Channel-specific `bad`/`limited` requires structured or explicit routing attribution; an HTTP 200 with completion is a reliable recovery only if the actual Provider matches the targeted slug or that pipeline/model's singleton `only` enforcement has been independently verified. A mismatched actual Provider is not a healthy target; it is an evidence gap, not an automatic strike. Any negative-control pin test uses the same fee budget, is low frequency/on demand, has a distinct supported/ignored/unknown result, and never adds an impossible slug to known channels. This calibration does **not** auto-discover new providers.

At chat Provider planning, first build the existing allowed list (configured/discovered source → manual exclude → durable hard/cooldown and account circuit). Then skip only that selected account's auto-held `(model, slug)` when another normally eligible candidate remains. If all normally eligible candidates are auto-held, use the existing strict/preferred safe order to pick one exploration target and cap the entire request to one real Provider attempt for that account. No auto route bypass when manual exclusion removed all; account replacement on a failed exploration must not create another real attempt. Session Provider hints from the sibling task are applied **after** the account-scoped hold filter; a hint cannot revive a held channel when another eligible candidate exists. For the all-held exploration, use pre-existing order rather than a stale hint.

## Recovery, administration, UI

A held triple stays held through stale/unknown checks, exhausted budget, schedule disable and restart, until a reliable successful probe of that same account/model/channel or an exact authenticated administrator recovery. Proposed `POST /api/providers/probe-recover` accepts exact `{accountId, model, provider}`, clears only this auto-probe state, leaves manual excludes/durable Provider quarantine unchanged, and returns a bounded accepted snapshot. Disabling periodic probing **does not silently clear holds**; the UI warns that recovery then requires the explicit action or re-enabling probes. Account identity rotation and deleted routes invalidate their own state, not another account's verdict. Projection labels hold, streak, checkedAt, outcome confidence, last account scope and age/unknown coverage; a globally selected model view must not falsely assert a single account verdict. Native controls/labels and `aria-live` are used in the model/account-scope console, with existing `api()`, escaping, draft/generation guards and server-state reload after writes. Show that calls may incur cost and the count cap is not a USD cap.

## Failure, rollout and rollback

Background persistence/network/cancellation errors must not block or penalize chat. Status publication is generation-fenced; duplicate ticks, manual validation overlap, config save and shutdown cannot create extra unbounded work. On shutdown, stop dispatch, cancel in-flight automatic probes and wait within the existing deadline before closing log stores/agents. No traffic is sent on fresh startup or after schedule disable, absent an eligible account, or after the rolling cap. Rollout requires an isolated temporary-DATA_DIR rehearsal and explicit later deployment authorization because the user chose **default-on paid checks** and durable metadata. Keep a tested disable switch plus per-triple recovery and an old-image/data rollback plan for schema changes; never run the old image against incompatible writable new state.
