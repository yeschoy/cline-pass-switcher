# 优化普通 JSONL 日志性能

## Goal

消除普通请求/错误 JSONL 在服务冷启动和追加热路径中的同步全量扫描与重写，在不改变诊断、安全、查询和保留合同的前提下实现高性能增量存储。

## Background

- `JsonlLogStore` 构造时同步 `compact()`，每次追加同步枚举/stat 段，每 100 条全量读取重写，最终请求还会再次执行组合容量扫描。
- 历史生产证据显示约 10.7 MiB 普通 JSONL 在 `server.listen()` 前造成明显冷启动阻塞和健康检查连接失败。
- 当前本地临时基准：5,000 条代表性追加约 3,607.9 ms，即约 721.6 µs/条。
- 详细日志已在独立任务中使用有界增量 inventory 优化；本任务仅处理 `DATA_DIR/logs/{requests,errors}-*.jsonl`。

## Requirements

### R1 — 非阻塞启动与真实可用性

- 服务先监听，再后台恢复既有普通日志目录。
- 恢复期间模型请求和新日志追加正常；普通日志查询返回安全明确的 `503 日志初始化中`，不得返回部分历史。
- 恢复失败不影响模型流量，但日志 API 必须报告安全不可用，不能假装完整。

### R2 — 高性能追加和维护

- 初始化完成后每条追加不得枚举、stat、读取或重写历史段。
- 不得再按固定 100 条全量 compact，也不得在每个请求后全目录执行组合容量扫描。
- 写入、滚动、保留和清理使用异步 I/O；CPU/磁盘维护不能长时间阻塞事件循环。
- 同机 5,000 条代表性追加必须至少比当前约 3.6 秒基线快 10 倍。绝对时间只报告，不作为跨机器硬门禁。

### R3 — 行为兼容

- 保持请求 50,000 条、错误 10,000 条、30 天、5 MiB 段和请求/错误组合 100 MiB 限制。
- 保持请求 `requestId`、错误 `(requestId, attemptIndex)` 身份去重，损坏完整行跳过、尾部截断容忍和原子替换。
- 保持全部过滤、1-200 limit、opaque cursor、stale cursor、安全投影和独立 clear 语义。
- 既有 JSONL 不迁移、不删除字段，新版本可直接读取。

### R4 — 安全和 fail-open

- 不增加正文、Header 值、会话、账号备注、代理或凭据字段。
- append/maintenance 失败只记录脱敏服务错误，不改变模型响应。
- 内存目录/队列必须有固定边界；恢复过慢或异常时不得无限积压诊断对象。

## Acceptance Criteria

- [x] 历史语料存在时服务已监听并可处理模型流量；日志查询在 ready 前返回 503，ready 后完整包含旧记录和恢复期间新记录。
- [x] 文件系统调用计数证明 ready 后普通 append 对历史语料执行 0 次目录扫描、历史读取和全量重写。
- [x] 5,000 条同机追加比 3,607.9 ms 基线至少快 10 倍，并记录启动、查询、维护、heap 和 event-loop 证据。
- [x] 保留/组合容量/段边界/去重/损坏/截断/分页/过滤/clear/重启兼容测试全部通过。
- [x] 查询稀有过滤时使用异步有界分段扫描并主动让出事件循环，不阻塞模型请求。
- [x] 普通日志安全投影和详细日志合同均无变化。
- [x] focused、integration、完整项目门禁通过。

## Out of Scope

- 不修改详细日志捕获、脱敏或 `DetailedLogStore`。
- 不引入数据库、外部依赖或新的持久 sidecar 数据库。
- 不改变日志 API 字段、UI 筛选器或生产保留上限。
- 不执行生产部署或清理生产日志。
