# Design: non-sticky load + health, separate pure-pool-capacity wait

## Boundary and compatibility

- Add opt-in `accountMode: "load-health"` for **non-sticky** requests. If `accountMode` or `accountPipeline.sticky` enables sticky behavior, do not change its account ranking, initial binding miss, HRW choice, or hit/overflow semantics; reject an incompatible new-mode + sticky configuration before persistence rather than silently overriding sticky. All six existing modes and persisted configs keep their behavior.
- Add optional top-level `poolFullWaitMs` (integer 0–30000; `null`/absent = inherit the *effective* `concurrencyWaitMs` at admission). `GET /api/accounts` returns the explicit value or `null`; `POST /api/accounts` missing field preserves the current explicit/inherited state (old clients), explicit `null` resets to inherited, integer updates it. Persist only explicit values or `null` as appropriate. Startup rejects an invalid explicit value without rewriting the operator's file. The existing `concurrencyWaitMs` contract remains unchanged for selected-account waits and RPM-only/mixed blocks.
- Only an owner-scoped, currently qualified candidate set with **every** candidate `maxConcurrent > 0`, `activeCount >= maxConcurrent`, and **no** candidate RPM-blocked is pure pool-concurrency-full. A single preferred account at cap while another is free does not satisfy it. Cooldown, ban, reserve, removed/disabled accounts, owner mismatch and exclusion do not count as waiting candidates. Under an active cache subpool use the active eligible set; keep existing one-at-expiry growth rules and avoid taking standby accounts just to call the pool not-full. Empty eligible sets retain the existing unavailable result.
- Keep one request-scoped admission start time. At every capacity wake recompute eligibility and block reason; select `start + poolFullWaitMs` only while the *entire* current candidate set is purely concurrency-full, otherwise `start + concurrencyWaitMs`. Switching state cannot add two full waits in series. If an account becomes available, admit without sleeping to deadline subject to existing sticky precedence. Use the effective timer for local concurrency 429 / Retry-After; preserve RPM's earliest reset and mixed block diagnostics. Where an existing `single`/sticky path waits on one account, first test the **whole qualified owner pool**, not that singleton, before choosing the pool timer. A binding's temporary fallback is not a permanent rebind. If the new field is absent, both deadlines coincide, so old timings are unchanged.

## Account choice

- Reuse `enabledAccounts`, `accountHasCapacity`, `rpmAvailable`, `tryLeaseResult`/`createLease`, pipeline quota groups, and current counters. Do not add a queue, scheduler, history store or alternate lease path. New mode ranks **available** accounts within the first admissible quota group, never across owner, reserve or hard-health filters. For this mode only, skip `healthSort`'s strict per-success-rate partition (it currently defeats any load ranking); keep quota group order and all other modes' grouping untouched.
- Proposal to validate with local simulations: prefer candidates whose known recent success rate is within 15 percentage points of the best known rate; keep unknown-sample accounts eligible as exploration rather than treating them as numeric 0 or 100. If no member of the preferred band is currently admissible, fall back to remaining admissible candidates. Among a band's members rank by current in-flight `activeCount` (not fabricated utilization for `maxConcurrent:0`), then known higher health, then reuse existing round-robin tie break. This favors distributing overlapping work among similarly healthy accounts and avoids repeatedly favoring a marginally better rate; it is not a prediction of upstream 429. If simulations show the band produces unacceptable concentration or clearly ill accounts, refine it *before* implementation and record the evidence. Do not expose an arbitrary tuning knob in v1.
- Keep `maxConcurrent:0` unlimited for admission; never interpret it as zero load. RPM remains an admission gate, never a surrogate success score. A failed Provider attempt stays on its leased account; account replacement is permitted only at the existing documented pre-stream path.

## Cross-layer data flow

- `server.js`: extend `ACCOUNT_MODES`, strict account-save validation, persisted normalization, `GET` projection, the common selection/wait helpers and the two legacy/pipeline call sites. Keep write atomic after full validation. Centralize pure-pool predicate and effective deadline choice; do not copy it independently into each branch. Preserve detailed/ordinary diagnostic safety projections and account-owner invariants.
- `public/index.html`: native select option plus an optional whole-pool wait input, empty meaning inherit. Account snapshot/draft/raw scheduling editor/presets/full save must round-trip explicit vs inherited state, preserve unsaved edits and reject invalid values before POST; server remains authoritative. Use the existing account snapshot/generation owner; do not reconstruct from table rows. Label old wait as primary/other admission wait and new wait as pure all-concurrency-full.
- Update `config.example.json`, `README.md`, backend/frontend/cross-layer specs. Do not change default mode or switch production configuration.

## Verification and rollback

- Isolated `DATA_DIR`/local mock upstream: six existing modes baseline; owner separation; mixed health/unknown and different limits; 6+1 simultaneous requests; pure-pool wait 0/nonzero with early release; selected account full but another idle; RPM-only/mixed with existing Retry-After; sticky hit/miss/overflow and cache expansion; cancellation/lease release; concurrent older-client save and restart round-trip; invalid POST and malformed config byte preservation.
- VM/UI draft tests and browser keyboard/focus/narrow-width check for new controls. Bench high-concurrency distribution and event-loop cost before claiming improvement. Revert the new mode to a legacy mode and set `poolFullWaitMs` to `null`/remove it to restore old behavior without data migration; rollback executable code and spec/doc commits together.
