# Current routing and load/health interaction (read-only, 2026-09-27)

## Evidence

- `server.js:614,1188,4933–4939` enumerates six persisted `accountMode` values and validates them on management writes. `public/index.html:240–248,1339–1422` owns the native select, raw scheduling draft and complete account save; `test/integration.test.js:1920–1950` covers six-mode legacy equivalence. New mode is cross-layer schema work.
- `server.js:1420–1463` filters hard account eligibility then atomically leases a capacity-eligible account with initial RPM reservation. `activeCounts` is an in-flight count and returns to zero on idempotent release; `maxConcurrent:0` is unlimited. `server.js:1504–1520`'s `least-connections` ranks smallest active count with RR ties (not utilization or health); `roundrobin` spreads by counter.
- `server.js:1610–1650`: `healthSort` is a **strict success-rate partition**; highest distinct rate is the first group, rated before unknown. Even with `accountMode:'least-connections'`, group-by-rate precedes load ranking, so a healthy top account with capacity wins until saturated. Rates are successes/(successes+degrades) from recent statistics, with no samples represented by `null` (`server.js:2794–2816`), not a measured probability of future 429.
- `server.js:1917–1997` chooses from the pipeline groups and falls back to a later group only on local capacity/RPM ineligibility. `server.js:1533–1569` applies legacy mode ranking only if no pipeline is active. `server.js:1581–1590` confines the active cache pool to sticky configurations; `server.js:1810–1915`'s existing stateful binding hit must keep the account or temporary-overflow only under documented conditions. Provider retries in `handleChat()` remain on the leased account; only a pre-stream documented account action may replace it (`server.js:4400–4490`).
- `concurrencyWaitMs` is a bounded admission deadline, not a mandatory sleep nor exclusively an “all accounts at maxConcurrent” timer. Multi-account non-sticky selection admits immediately if any eligible candidate has concurrent and RPM room, and waits only if the eligible pool is blocked by capacity/RPM (`server.js:1534–1574,1950–1997`). `single` waits on the selected account even if another is free; legacy sticky with a fingerprint waits on its HRW primary before fallback (`server.js:1538–1557`); a sticky+healthSort stateful binding hit normally waits on its bound account, with the existing role-aware low/high immediate temporary-overflow exception (`server.js:1813–1898`). Sticky-only cache-pool selection can skip a saturated primary and try other active members immediately (`server.js:1917–1950`), then may grow-one under stricter finite-concurrency-only conditions. Without an identity fingerprint or a valid binding, “original account” need not exist. Capacity releases wake waiters before the configured deadline; exhausted wait returns a local 429 with bounded Retry-After. Provider retries on an already leased account do not reuse this wait.
- `maxRpm` protects only the local rolling window and cannot prevent externally imposed upstream per-account 429. Selection must preserve `blockedBy`/Retry-After classification; `maxConcurrent` and `maxRpm` are guardrails, not load-sharing objectives.

## Design risks to resolve

1. If a new mode only changes `strategyRank`, `healthSort` will still create one-account top-rate groups and defeat load balancing. The mode needs one coherent ranking owner that handles **both** signals without duplicating quota/hard-eligibility/binding logic.
2. Prefer current in-flight count plus explicit `maxConcurrent`/RPM admission facts; unknown/unlimited limits must not be treated as known zero or fabricated 100% utilization. A health-vs-load tolerance and low-sample handling need executable tests.
3. The request says “without stickiness”; use the conservative boundary of configurations with sticky disabled. A sticky configuration's first binding miss is not part of this new mode without separate approval; preserve existing HRW and stateful binding behavior. The new pool-full wait is separate and may apply to sticky configurations when the strict pure-concurrency condition is met.
4. User confirmed the pool-full timer applies only when every currently eligible account in the owner-scoped pool has a finite `maxConcurrent` and is at that cap, not to RPM-only or mixed blocks. A single selected/primary account at its cap while another has room is not pool-full. Missing new setting must inherit the old timer. Existing full-save account drafts, tests, README and backend/frontend specs require synchronized changes. No live mode switch is included.
