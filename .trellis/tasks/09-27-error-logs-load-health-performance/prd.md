# 错误诊断、无粘性负载调度与高并发性能调查

## Goal

让管理员在安全边界内看清失败的完整可用诊断，让无粘性请求在高并发时兼顾账号负载与健康度，并找到请求链路中有证据支撑的性能改进点。

## Background and confirmed facts

- 用户反馈错误日志不像详细日志那样展示全部，并明确选择在错误日志板块查看失败请求的**客户端入站请求 Header/Body、上游请求 Header/Body、上游响应 Header/Body、最终客户端响应 Header/Body**（不是仅跳转详情页）；担心只按最高健康率选号造成账号集中和 429，并要求新增无粘性负载＋健康度模式及调查高性能优化点。生产 429 的实际成因尚未验证。
- `server.js` 的普通错误行只存脱敏限长的 `reason`；`public/index.html` 可展开普通行的 JSON，且已提供精确匹配 attempt 的“查看错误详情”按钮（`public/index.html` 1648–1663），但这不意味着当时确实采集或保留了详细正文。`.trellis/spec/backend/logging-guidelines.md` 明确禁止将原文正文写入普通错误日志。
- 当前健康排序以账号历史 success-rate 分层；可用并发和 RPM 在准入处过滤，而非主动按当前负载分流（`server.js` 1533–1569、1610–1650、1917–1997）。用户进一步要求新增**整个账号池都满时的等待时间**配置，与现有粘性首选/绑定账号等待区分；已同意新配置仅针对同一客户端密钥归属下所有当前合格账号同时达到并发上限的纯并发满载，不重新定义 RPM/混合阻塞等待。现有 `single`、`sticky` 等策略不能被无意更改。
- 用户同意先复用 `raw-full` 而不是新增错误专用四段捕获。它已采四段但对成功请求也捕获；`raw-error` 只采失败上游 attempt 的请求/响应两段（`lib/detailed-log-capture.js` 440–580）。原文 Header 的认证/Cookie 值仍不可见，Body 也有大小与资源界限。现有 `.trellis/tasks/09-26-production-raw-body-enablement/` 是独立的生产原文采集启用与验收任务；本任务不替它执行生产配置、资源或部署变更。

## Child deliverables

1. `09-27-error-log-detail-visibility`：在错误日志板块呈现失败请求四段已采集链路，区分选中 attempt 与请求级入站/出站，保留普通 JSONL 与详细存储的安全边界。
2. `09-27-load-health-account-routing`：新增可选择的无粘性联合调度和独立的全池不可准入等待设置，在容量、健康和兼容性边界内验证并发分流。
3. `09-27-high-concurrency-path-investigation`：对实际请求生命周期做本地、可复现的瓶颈调查，给出按收益与风险排序的优化建议。调查不自动授权实施所有建议。

## Requirements

- 三项交付可独立规划、验证和归档；父任务只管理共同约束与最终集成验收。
- 不将凭据、消息、原文响应、Header 值或其他敏感数据写入普通日志/研究产物；缺失的历史详细正文无法补回。
- 新调度与池等待设置必须保留现有账号所有权、硬隔离/冷却、额度保护、并发/RPM、租约释放、会话粘性及首包后不换号等边界；旧配置缺少新字段时沿用当前等待语义，不能承诺消除所有上游 429。
- 不使用生产密钥、生产数据或付费上游进行测试；不未经单独授权修改生产配置或部署。

## Acceptance criteria

- [ ] 三个子任务各自有可验证结果，父任务综合对照安全、兼容性与高并发目标。
- [ ] 日志与调度变更有端到端和管理台验证；性能建议区分实测事实、推断与未测项目。
- [ ] 对生产 429 的归因只在拿到匿名、明确的观测证据后陈述；本地模拟不冒充生产收益。

## Follow-up request pending clarification

- 用户追加“目前看到密钥长度太短，需要生成设置长一点”。只读检查确认：独立客户端密钥由服务端使用 32 字节随机数生成，格式为 `cps_` 加 64 个十六进制字符（共 68 字符、256 位随机强度）；Legacy 客户端密钥目前由管理员手动填写，独立密钥的一次性展示是单行只读输入框。尚未确认用户指哪种密钥，不能擅自轮换现有客户端凭据，也不能仅凭界面可见宽度判断实际强度。确认后再决定是否新增独立子任务，并同步更新父任务的交付范围和技术/执行计划。

## Review boundaries

- 已确认池满等待仅覆盖纯并发满载。两种等待条件先后出现时，不应将完整超时串行相加导致单次请求意外延长；设计采用从同一次准入开始计算的场景截止时间。
- 按安全/性能原则暂定同板块单行显式展开、按需读取并在离开/切换时清除原文，不自动批量下载整页；最终规划审核时向用户明确呈现这一交互默认值。不得默认突破普通日志、Header 安全边界或自动开启原文采集。
