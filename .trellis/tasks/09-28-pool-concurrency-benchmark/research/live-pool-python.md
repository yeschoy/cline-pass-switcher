# Host-only Python 3 benchmark candidate (review before live use)

The first production run on `cline-pass/glm-5.3-flash` and the subsequent direct-model DeepSeek dry-run both stopped on two HTTP 500 attempts; neither established an RPM threshold (see the first/second-run reports). A separate, later two-request diagnostic succeeded with alias `pc/deepseek-v4.1-flash`, resolved target `cline-pass/deepseek-v4.1-flash`, streaming and 256 tokens, but did **not** establish a capacity/SLO or the cause of those earlier 500s. The locally revised capacity mode now fixes that alias, uses only SSE and 256 tokens and requires a **new alias-bound preflight and independent paid-run approval**; it has not been run against production. The earlier Node generator remains unchanged. This Python 3.9+ stdlib alternative uses no remote file: the fixed documented public HTTPS ingress, one hardcoded operator-approved alias/target, and **Legacy only if the privately entered client key matches that owner**. An additional-owner key or unknown key fails closed; it never silently substitutes the configured Legacy key or claims that owner's capacity.

**Review the wrapper and generator before invoking them.** Only the human operator at a local terminal should run the wrapper; never paste a credential in chat, arguments, environment, redirected stdin or a transcript. Preflight is read-only (no chat):

```bash
python3 -B .trellis/tasks/09-28-pool-concurrency-benchmark/research/live-pool-invoke.py --preflight
```

`--live` is deliberately separate and requires `--accept-observable-only-guards`, **only after a fresh preflight of this revised source**, independent review of ingress/model pricing/version/owner, and explicit operator acceptance of this new streamed capacity workload and the fact that an internal upstream 429 or provisional protection cannot be stopped instantly. Those flags are an invocation gate, not evidence of earlier consent. Do not invoke live as part of offline verification. The explicit live command for a separately approved future run is:

```bash
python3 -B .trellis/tasks/09-28-pool-concurrency-benchmark/research/live-pool-invoke.py --live --accept-observable-only-guards
```

This implementation has **no additional-owner measurement mode**; if preflight rejects the key, stop and design an owner-specific safe projection instead of trying another credential.

The local wrapper opens `/dev/tty` with no echo; if an embedded terminal provides no usable controlling TTY, macOS displays a hidden-answer dialog instead. It never falls back to an echoed prompt. It validates the repository-local SSH identity is an ignored regular file with mode 0600 without opening it, and uses SSH with no user config/forwarding, BatchMode, pinned host-key checks and bounded connect/total timeouts. It supplies the non-secret base64-encoded Python source in the remote `sudo -n python3 -c` **code argument**, with the key plus one newline as the **only SSH stdin bytes**. The wrapper keeps that stdin pipe open until SSH exits, drains bounded stdout in parallel (stderr is discarded), terminates/kills local SSH on timeout or Ctrl-C, then closes the pipe. The remote credential reader stops exactly at the newline without consuming later bytes; its monitor checks for EOF or extra stdin bytes at startup and about every 0.2s during the run. Either event vetoes new sends and closes active client sockets. SSH termination/disconnect is **not** a guaranteed remote kill: network partitions that leave the remote session open, paused processes, outstanding sends and upstream attempts can survive temporarily. The remote generator's own ~295s deadline and request timeouts are a second bound under normal scheduling, not an OS-enforced orphan-runtime guarantee. If stronger assurance is required, obtain an independently authorized remote watchdog before live use. Neither the wrapper nor remote code creates files; do not use a shell transcript capturing input or pipe raw Docker/config output. It discards remote stderr, validates every nested output field against fixed bounded types/enums/timestamps/image digest, rejects unexpected keys, and never prints the key. Interrupt in the foreground is the emergency stop, but already-sent work may still bill, including on SSH loss/timeouts. The script uses `docker inspect --format` into **private in-memory** subprocess pipes, compares the supplied key to effective Legacy (`PROXY_KEY` only if it agrees with the stored value), reads only fixed root-private host config and metadata privately, and never writes/prints either input. It does not publish upstream account keys, admin credentials, additional client keys or hashes. A different mount, missing host Python/Docker helper, unexpected JSON size/schema, stale/ambiguous Legacy credential, runtime-injected `CLINE_PASS_KEY` account, full/raw diagnostics (existing error-only mode stays unchanged), unknown model or unhealthy ingress/service fails closed **before chat traffic**. A persisted security edit can supersede a startup override; if stored and environment keys differ the benchmark refuses to infer runtime identity. The comparison is repeated during monitoring but is sampled, not atomic with every send; a concurrent key rotation is not provably intercepted at the instant it occurs.

## Preflight and continuous guards

- Verify the supplied stdin key equals the effective Legacy client key and is not an additional-owner key, then verify container is running/healthy on a stable image/start time, its data bind matches `/opt/cline-pass-switcher/data` → `/data` (RW), `DATA_DIR=/data`, hard memory limit ≥256 MiB, host config owner is Legacy and contains enabled keyed accounts, no persisted protection/cooldown/quota hold, the **exact** `pc/deepseek-v4.1-flash` alias resolves to known `cline-pass/deepseek-v4.1-flash` without a chained alias, existing error-only diagnostics (if any) stay unchanged while full/raw capture is refused, and global lifetime request count is observable. Every enabled keyed Legacy account must resolve its complete `perModel[resolved target]` override or inherited global `perModel[resolved target]` to an explicit integer `maxRetries` of 0 or 1; missing/null, higher or malformed values fail preflight. This conservative gate includes standby accounts that could become eligible later. Reject initial CPU >80% or RSS ≥70% of the configured container memory limit. Public GET `/api/meta` must return `configured=true`, `authRequired=true` and exact known HTTPS `proxyBase`; this is not an authenticated admin check. A zero/anonymous Legacy key is rejected.
- Every ~2s re-check runtime identity/health, memory/CPU (`docker stats`), config digest, owner counts, persisted account protection and metadata pool target. Stop if CPU >max(90%, baseline+65 percentage points) or RSS >min(85% limit, baseline+128 MiB), and on any Docker/JSON error. Count a **certain minimum** of external completions only when the persisted global lifetime counter grows more than the number of test requests already sent; stop if this certain minimum reaches 30 within the short run. Ordinary customer traffic is expected, and this estimate misses concurrent external requests hidden behind the test's outstanding completions: it is NOT a proof of idle background traffic. For actual production acceptance, an independently authorized, request-attributed safe aggregate monitor is still required. Process-local provisional quota holds, active leases, rolling RPM reservations, per-request log attribution and event-loop delay are not exposed by the file projection: they remain **unobservable**, never reported as zero. In particular, this checker does **not** request an authenticated live `/api/accounts` RPM/active projection; the persisted config/account-state comparison is not proof of current RPM headroom or server in-flight leases. If these gaps violate operator guardrails, do not invoke the generator until an authorized real-time aggregate projection is available.
- Host config/state reads are private projections only; output includes the validated running image SHA-256/start timestamp and safe account counts, not IDs or account names, paths, URL, model, proxy details, response bodies, credentials or config hashes. The script does not change production configuration, diagnostic mode, logs, process, image or files. A script crash, SSH loss or forced termination may leave upstream work already sent/charged; SSH disconnect is not an automatic rollback.

## Workload and outputs

Streamed `/v1/chat/completions` with the fixed client alias, fixed `Reply OK.` prompt, `max_tokens=256`, random distinct `session_id` and no client retries. Only HTTP 200 with SSE Content-Type, exactly one attempt, a non-whitespace `choices[].delta.content`, complete `[DONE]`, no error event/envelope (even falsey `error`), and clean EOF counts as useful success. An incomplete/oversized/malformed/error stream or stalled read is a failure and stops; even `[DONE]` without content is not useful. The first streamed dry request must pass. The bounded diagnostic parser is reused: ≤64 KiB per line/event and ≤256 KiB total; a response-owned socket timeout applies to connection-closing HTTP/1.0 as well. Paced 60/120/240 RPM ×6s (missed ticks dropped), 350 RPM ×120s if guards and budget permit, then synchronized 1/2/4/8/16/32/64 offered-request bursts. At the synchronized actual HTTP send seam (after connect/TLS), the rolling 60s limiter and abort/deadline/monitor guard are rechecked across all stages. A slot is reserved under the same lock **before** `conn.request()` and its timestamp advances to the end of that serialized call even if a partial write fails. The slot remains occupied for a further 60s after that end: this intentionally under-offers if a transport write is slow, rather than releasing an early timestamp while later bytes are sent. A blocked send already handed to the transport cannot be unsent by abort. This provides a conservative ≤350 downstream sends in any 60s window under normal clock/scheduler progress, not a guarantee against remote retries or an OS-level watchdog. Other limits are ≤900 downstream sends, ≤5min with five seconds reserved for bounded shutdown, ≤64 pending/in-flight client workers (emergency cap, **not** measured server lease concurrency). A queued or connecting worker is not counted as sent; a request already being handed to the transport cannot be revoked retroactively. The small HTTP write is locked against abort and uses a 1s socket-send timeout; the 30s response timeout is outside that lock. Emergency SIGINT/SIGTERM marks stop immediately, including if delivered during main-thread admission. The server's per-account Provider plan allows at most `maxRetries+1` real attempts; `handleChat` allows at most **two** account chains only for the documented pre-stream account removal (`server.js:4480-4519`). Thus explicit `maxRetries<=1` on **every eligible Legacy route** gives a worst case of four upstream attempts per downstream chat. The generator reserves four paid attempts for every pending worker and reconciles on completion using `X-Cline-Attempts` (missing/invalid counts consume four conservatively); it never admits a new worker when observed-or-reserved paid attempts could exceed **900**. Any non-200 with `X-Cline-Attempts>1`, or any response with >4 attempts, stops immediately as unexpected fanout. This accounting depends on stable, correctly normalized routes and this server code; a simultaneous external config/code change or upstream charging policy cannot be guaranteed by the client. Continuous digest/image checks detect drift only at their sampling interval. Stop at the first **downstream-visible** 429, 503/protection, auth/invalid reply/fanout/oversized response/network issue, two 5xx/timeouts in rolling 20, <95% successes in full rolling 20, or p95 >2× first successful baseline **and** >10s. Socket timeout 30s (SSE reads also enforce an absolute 30s deadline from the send seam); an observed streamed-body timeout stops immediately. After a stop shut down both connection and any detached response-owned socket (HTTP/1.0 / `Connection: close`), then allow at most one second local drain. This interrupts an active SSE read under normal OS socket behavior; a worker stuck before socket creation or inside uninterruptible host code can still remain unresolved. A failed/partial transport handoff remains conservatively counted as offered and keeps its rolling-rate slot, even if no complete request reached the server. Sent work may still bill/finish upstream; `unresolvedClientRequests` is reported. The first successful sample is a weak baseline; independent safety guardrails can be stricter. An upstream 429 can be hidden by the service's configured Provider retry and reach this client as a later 200; the runner then stops on `X-Cline-Attempts>1`, **not at the instant of that upstream 429**. Process-local provisional quota protection can likewise precede persisted metadata; neither is observable in real time by this read-only host script. Live execution requires the operator to accept this specific guardrail limitation or an independently authorized attempt-level observer. Do not claim instantaneous upstream-429/protection detection.

Per stage: UTC window, `plannedOffered` (burst target or one dry-run; null for time-paced stages), `budgetCensored`, actual offered/completed/useful successes and `unresolvedAtStageEnd`, measured wall duration (including drain), completed and successful RPS, success-only nearest-rank p50/p95/p99 with sample count, known/summed attempts, client-side overlap peak and bounded error categories. An aborted stage freezes one locked counter/latency snapshot; a late worker may settle afterward, but it cannot retroactively alter that stage's reported completion count. A worker externally cancelled before a stream is credited cannot become a success. `successRate` uses **completed** requests as its denominator; `unresolvedAtStageEnd` and `offered` must be read alongside it. Latency quantiles are end-to-end client wall times for **completed useful SSE** through EOF, not time-to-first-token or all requests. Stage RPS divides completions by the stage's actual measured span (including drain); millisecond bursts can report high instantaneous quotients, never sustained offered RPM. The global attempt summary snapshots observed plus still-unsettled worst-case reservations after the bounded final drain. 429 with zero attempts is local; positive attempts is `attempted429` (can be upstream 429 OR local retry-RPM after an earlier attempt); missing attempt header is unknown. **Do not call either of the latter upstream 429 without separate authorized request-attributed evidence.** Short/partial stages, incomplete two continuous 60-second final-rate windows or a safety stop cannot establish a sustained rate. CPU/RSS are sampled container indicators, not per-request cost; Python client peak is not server leases or upstream concurrency. Event-loop delay, exact background owner attribution, startup RPM and in-memory protection remain unavailable. A stage named `burst_64` with fewer than 64 offered requests is **not** a 64-request test: report its actual transport handoff count, actual peak client overlap and `budgetCensored=true` if the four-attempt reservation budget stopped admission. A paced stage cut short by that budget also carries this label; omitted stages were never attempted. Budget exhaustion is not a capacity knee. A successful result is at best a lower bound under this owner, **SSE** workload, release and external load, not the pool maximum or evidence for other client-key owners, non-stream traffic, proxies, long prompts or unlimited accounts. Do not equate the 64 cutoff or 350 RPM ceiling with actual capacity.

## Separate alias/stream diagnosis (not an RPM benchmark)

The earlier DeepSeek dry-run also stopped on two HTTP 500 attempts. The diagnostic remains a separate non-stream-then-stream two-request mode; the revised `--preflight`/`--live` capacity modes now also validate this exact alias but execute an all-stream workload. A capacity preflight is not permission to perform a diagnostic run or vice versa.

Only after local review, operator approval of paid work, and a **fresh** alias-bound read-only preflight, the operator can invoke the separate diagnostic. Do **not** run these commands as part of automated verification; no key may appear in argv, stdin redirection, environment, files or chat. Exactly one non-stream request with `max_tokens=256` is tried first; only a useful 200 with exactly one attempt allows one SSE request with the **same** alias, `Reply OK.` prompt and output cap. It requires a non-whitespace `choices[].delta.content`, complete `[DONE]`, no in-stream error (including `type`/`object` error envelopes) and clean end; 64 KiB per line/event, 256 KiB total, 30s per chat read budget, and error/status/attempt guards apply. Output contains only fixed safe summary fields, **never** SSE bodies, prompts, raw errors, account/provider identity, private paths or credentials. Test mode refuses non-`http://127.0.0.1:<port>` targets and never reads Docker or production data; tests check dry-run first-429/200-error behavior (including falsey error fields), Legacy equality/additional-owner rejection, stdin bounds, wrapper SSH-stdin-only transport with a synthetic local subprocess held open through output, preflight route rejection, delayed-thread abort/deadline/rate guards, four-attempt reservation, secrecy of stdout, monitor veto and protection gate.
