# Request-path differential probe (2026-09-28)

## Isolation and replay

The retained `request-path-bench.mjs` locates the repository with `git rev-parse --show-toplevel` from its own directory, so it remains runnable after Trellis archives this task. It accepts **only the two reviewed full commit IDs** below, reads committed `server.js` plus every tracked `lib/*.js` and `public/index.html` from that ref via Git, checks every instrumentation seam, and writes a disposable instrumented ESM server into an OS temp directory. It refuses to run if the current `test/admin-fixture.js`, `package.json` or `package-lock.json` differs byte-for-byte from that ref. Only installed `node_modules/` is symlinked; verify its declared dependency versions with `npm ls --depth=0` (this is **not** a full installed-tree integrity proof). `git diff 7eeb3b220e1c2071056d5c763f5d12af0b946a2e 378ff1f03112fc71d029508d1922ab230dfe8635 -- lib` is empty; these libraries are identical for this A/B. The original recorded runs predate this hardening and linked current `public/` (B's UI even for A); that file differs across refs but is read only by GET `/` or `/index.html`, which this workload never calls. They also linked current `lib/`, which was byte-identical for A/B; the strengthened replay avoids future mixed-source runs. Each case/repeat creates independent temporary `DATA_DIR`/admin state. The child receives a **whitelisted** environment (no inherited operator credentials), binds to `127.0.0.1` on a throwaway port, uses only generated synthetic keys and a local HTTP mock. Reviewed benchmark requests never call the separately available official-docs management fetch; this is source/route isolation, **not an OS egress firewall**. Raw mode uses `NODE_ENV=test`, the test-only 2 GiB memory override and explicit readiness **in this disposable child only**; the runner first requires ≥2 GiB actual reported host/cgroup memory (unknown Linux limits fail closed). This minimum does not validate production raw availability or memory headroom under load. The parent discards every body (including diagnostic retrieval: only manifests/descriptors, never text), prints aggregate numbers only, and removes the entire temp tree on normal completion, errors and process exit; SIGKILL/power loss cannot guarantee cleanup. Do not run with real configuration, bodies or credentials.

Environment: Apple M4, 24 GiB physical RAM, Darwin 24.6.0/arm64, Node v26.8.1, local filesystem, 2026-09-28. Measured commit A: `7eeb3b220e1c2071056d5c763f5d12af0b946a2e` (pre-feature); B: `378ff1f03112fc71d029508d1922ab230dfe8635` (integrated). The working-tree server is **not** substituted for B. Only synthetic inputs, not host CPU contention, OS cache or GC timing, are controlled. Each repeat starts a fresh child. Run:

The script emits **one JSON summary per repeat** (plus a header); no output redirection is needed. Default `--cases` includes new cases that A cannot support; always specify an explicit subset on A. `--repeats` is 1–5. The four invocations above specify comparable case subsets; the recorded measurements were executed in separate routing/dense/diagnostic/paused-SSE batches but use the same per-case setup. Prior archived 09-25 scripts use their then-live task-directory paths and are not directly runnable at the archived location without reviewing/repairing those paths; we inspected their temporary `DATA_DIR`/loopback behavior but **did not rerun or include their numbers in this A/B**. ## Workload and measurements

- Plain JSON body 340 bytes; SSE 339; large 1,048,660 or 6,291,540 bytes of fake repeated `x` characters. `/v1/chat/completions`, one mock Provider, `maxRetries: 0`, no paid catalog/quota. 1/2/10 account count; roundrobin/sticky/load-health; sticky uses synthetic explicit session identities. Success mocks take ~1 ms timer, slow mocks add 40 ms; 429 mock returns 429 to distinguish Provider rejection from local admission. `/v1/chat/completions` returns `X-Cline-Attempts`/`X-Cline-Account` summaries. The harness rejects unexpected mock paths/credentials, checks that response-account counts equal mock per-account attempts, asserts attempt-header totals equal mock hits, and attributes 429 with zero attempts to local admission; only the deliberate 429 mock may contribute upstream 429 (one attempt, no retries). For upstream-429 each request selects/leases once and performs exactly one attempt on that account; account distribution across **different requests** is not within-request failover.
- Default route sweep: 96 requests at concurrency 12 in eight 12-request waves; 12 sequential successful warmups per case, excluded from measurement. Fixed capacity: 2 × maxConcurrent=1, 24 requests at concurrency 12, 40 ms mock, `concurrencyWaitMs` 0/80; B-only `poolFullWaitMs=80` with normal wait=0; **no warmups** to avoid lease/RPM contamination. Ten-account slow: 48 requests, concurrency 12, per-account maxConcurrent=1, wait=80. Local RPM: 4 permits/one minute, 24 requests in two waves of 12, no warmup. Upstream 429: 48 requests, concurrency 8, no warmup. SSE: 48 requests, concurrency 8, mock sends first event then `[DONE]` after 40 ms. `ssePaused`: 12 requests in 4-request waves, each 4 MiB-ish SSE response, reader pauses 120 ms after its first chunk; mock respects `write(false)`/`drain` and counts stalls, 12 sequential warmups are excluded.
- Differing-health seed uses a real successful request to create version-5 metadata, restarts with known health for `a0` (9 successes/1 degrade) and `a1` (2/8); remaining accounts unknown. Dense cases copy one schema-valid minute bucket into the last 1,200 minutes (a synthetic corpus with **inconsistent historical lifetime ledger**, not real traffic). Warmup/measurement and comparison use identical synthetic state per mode but host files/cache and child GC differ. Source scans 1,200 buckets per projected account in these cases. No 50k-cell cap or production history distribution is approached.
- Diagnostic profiles: off, sanitized `error` (both success and 429 failure), sanitized `full`, accepted `raw-full`. Small: 48 measured requests at concurrency 4. 1 MiB: 12 at concurrency 2. 6 MiB: six at concurrency 2; only two sequential warmups there instead of 12, to bound fixture disk/memory. Error-429 comparisons have no warmup. Details are queried via authenticated manifest/list after completion without reading the saved bodies; roots/descriptor states/drop reasons are measured deltas after warmup. A one-second settle for 6 MiB and short poll for smaller profiles give async publication time. These diagnostic timings use highly compressible fake `x`, not production content or redaction-secret distributions.
- Client wall time includes full response consumption; requests are wave-limited, so throughput is `completed requests / measured wave span`, **not** maximum sustainable RPS. Latencies are sorted nearest-rank p50/p95/p99; for n=6, p95/p99 is literally the maximum. Warmup count/wall/latency appears separately in each JSON line. Both in-child `responseMetrics` (sampled when clients complete) and `metrics` (after async publication/80 ms quiet time, or one-second large-case settle) include CPU, peak sampled RSS/heap, 5 ms-resolution event-loop delay and synchronous section timings. CPU is process user+system, not per-path; timer max is not request p99, and 10 ms memory sampling can miss transient peaks. Detail publication/polling may be included in total CPU, not in response CPU. Fresh process start/login excluded from each measured window, but warmup **state** (connections, stats, diagnostic roots) carries over. The temporary per-call wrappers, 5 ms event-loop histogram, 10 ms memory timer and metrics endpoint itself introduce overhead/GC; timed sections are from an **instrumented server**, not an uninstrumented production profile. Stage wrappers are inclusive and asynchronous durations overlap; `readBody` includes network accumulation, while subsequent `JSON.parse`/validation and detailed-store redaction/publication were **not separately timed**. `clineRequest` measures upstream response-header/first-result handling, not complete streaming. **Do not sum nested section totals or mistake `runChatChain` in SSE for total streaming duration**. Metadata temp write/rename timings are not fsync/power-loss durability guarantees. No sustained steady-state test, raw near-35-MiB cap, retry fanout, real downstream `write(false)` counter or calibrated instrumentation-overhead control was run; this remains a bounded wave/safety probe.

See `measurements.md` for run-by-run bounded summaries. Statistics, startup/cold catalogs, ordinary-log recovery and browser DOM costs were investigated with different inputs in the archived 09-25 reports and are **not directly numerically comparable**. No TLS/proxy saturation, paid upstream, slow disk, 100k-root store, browser UI, production traffic or sustained capacity/SLO was tested here.
