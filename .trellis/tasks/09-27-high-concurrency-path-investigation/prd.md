# 高并发请求链路性能调查

## Goal

识别 Cline Pass switcher 从 HTTP 入站、选择/租约、上游尝试、流式传输到日志/统计完成链路的可证实瓶颈，优先推荐低风险、高收益的优化。

## Background

- 用户要求调查哪个链路可以优化，目标是高性能；尚未给定生产 p95/p99、并发量、流量模型或可公开的生产遥测。
- 既有 `.trellis/tasks/archive/2026-09/09-25-whole-service-performance/research/` 已涵盖全服务合成调查并落地 metadata 紧凑写入；大历史数据的同步终态写入、`/api/statistics` 聚合、冷目录/目录恢复等已有量化结果，不能当作本次的新发现重复实现。`.trellis/tasks/archive/2026-09/09-21-error-detail-log-performance/research/performance-validation.md` 还测过单次接近 5 MiB 的脱敏耗时约 102 ms。这些都不是当前生产瓶颈的证明，详见 `research/prior-evidence-and-gaps.md`。

## Requirements

- 复用上述已完成调查和可安全重跑的合成脚本，只对当前源码与本次新需求的证据缺口做差分：多账号无粘性高并发、新联合调度前后、按需诊断与 `raw-full` 的成本，以及必要时大历史 metadata/慢上游/SSE 的影响；区分账号准入、Provider/网络、诊断/持久化与管理 UI。
- 用临时 `DATA_DIR`、本地 mock 上游与可重复工作负载验证候选热点；记录精确源码版本、环境、负载、样本/误差、吞吐、延迟（含尾部）、event-loop 延迟、内存、诊断省略和本地/上游 429 分布，避免将上游耗时归咎于本服务。
- 形成按收益、风险、复杂度及兼容性排序的调查报告，标出事实、假设和仍需遥测验证的项目；任何实质性优化实现都需独立评审，不因调查而默认改造运行时架构。
- 不使用生产数据、密钥、付费上游，不触碰生产环境或配置。

## Acceptance criteria

- [ ] 提供可复现的本地测量方法、原始摘要数据和代码路径证据；和历史基准可比时说明差异，不可比时明确标注。
- [ ] 至少给出各候选瓶颈的有/无证据结论及排序建议，包含可能增加复杂度或破坏安全/兼容性的反例。
- [ ] 对尚未获得的真实生产流量特征列出最小、脱敏的观测需求，不把合成结果宣称为生产收益。
