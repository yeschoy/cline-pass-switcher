# Local selection-performance evidence (2026-09-30)

Environment: macOS Darwin arm64, Node v26.8.1, one `node server.js` process with a temporary `DATA_DIR`, loopback HTTP mock upstream and synthetic credentials. The repository's `Dockerfile` has one `CMD ["node", "server.js"]`; both Compose examples declare one app service and no replicas or cluster worker launcher. This proves only the checked-in single-process deployment shape, not an operator's unseen external topology.

## Local proxy burst

`node --test test/workflow-integration.test.js` ran 43 synthetic accounts with `maxConcurrent: 6`, `maxRpm: 0`, a fixed43-member active pool and a held local upstream. All 258 leases became 258 observed HTTP requests at the mock upstream with the512 default; Agent-queued requests were0. The next request got local429 and did not increment a counter. A separate two-socket override admitted3 leases while only2 reached upstream, proving the remaining1 was Agent-queued. With invalid `CLINE_PASS_DIRECT_MAX_SOCKETS=0`,513 leases yielded512 upstream arrivals and1 Agent-queued request until a socket was released; zero demonstrably fell back to512, not unlimited. These are process-local stages: a lease does not by itself prove an upstream request was sent.

A500-request burst with the same cap yielded 258 leased and upstream-in-flight,0 Agent-queued,242 local429, and exactly6 selections/active leases on each of43 accounts. On the focused run, admission settled in664.5ms; all500 responses settled in984.2ms, about508 requests/s for this short local scenario. Another isolated run took811.0ms, about617 requests/s. The server-side test-only `perf_hooks.monitorEventLoopDelay` preload observed event-loop p99 50.40ms/max295.96ms in the focused run and p99/max310.38ms in the isolated run. Burst scheduling and synchronous persistence contribute to this delay; the two samples do not establish steady-state or production latency. No real upstream/IP capability was measured.

The focused43x6 run produced a60,760-byte `metadata.json` after completions. In the500 test, the preload measured259 compact snapshot writes (including startup),380,623 cumulative serialized bytes, mean `fs.writeFileSync` time0.066ms and p950.105ms; this excludes JSON serialization, stat, rename, scheduling and filesystem power-loss durability. ## Microbenchmark

Run `node .trellis/tasks/09-30-selection-workflow/research/selection-microbenchmark.mjs` to repeat the warmed loops. The reproducible run imported the real `rankWorkflowCandidates()` with43 candidates and measured full least-selection ranking14.60 microseconds/call over20,000 iterations. A synthetic43-account config SHA-256 over JSON took3.43 microseconds/call and a43-account counter-snapshot `JSON.stringify` took1.00 microseconds/call (each20,000 iterations). A surrogate uncached health lookup scanning1,162 minute buckets x43 accounts (49,966 account-minute cells) took516.64 microseconds/call over200 iterations. An earlier inline run on the same host yielded16.71/3.83/1.12/538.67 microseconds respectively. The health figure is a scan surrogate, not a direct timing of `successHealthProjection()`. The real runtime now caches account health projections within a statistics generation and minute, invalidating them on statistics prune/commit and account save; occupancy, RPM and hard eligibility remain live. On these measurements, repeated health scans were the useful target; replacing the small ranking sort or config hash would add state for a much smaller potential gain.

## Guarantees and limits

Ranking, hard eligibility, capacity/RPM reservation, slot claim and count increment run without `await` in one Node event-loop turn. Reset writes its snapshot before publishing, and a failed reset leaves live counts intact. Each new selection writes a compact atomic-rename snapshot synchronously; there is no debounce loss window. A failed write leaves an in-memory count and visible persistence error, so a subsequent restart can lose that unpersisted increment. The writer does not call `fsync`, so sudden power loss cannot be promised durable. Multiple instances sharing a data directory would each have independent leases/RPM and non-atomic read-modify-write counters; the checked-in deployment uses one process, and no Redis/database was added. The local mock does not measure remote upstream limits, proxy-Agent32 socket constraints, production network throughput, or downstream intermediary queues.
