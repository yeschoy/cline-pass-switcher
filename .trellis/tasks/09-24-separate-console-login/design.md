# Independent console login — implemented design

## Boundary

Split the current `authOK()` shared PROXY_KEY guard: model routes retain the client key; `/api/*` management (except deliberately public `/api/meta` and new authentication exchange) requires an independent admin session. Exhaustively enumerate admin routes rather than patching only `/api/models`. The static page can remain public only if it embeds no sensitive data. No management endpoint may fall back to client Authorization/X-Admin-Key after migration.

## Credential lifecycle

A single local administrator password is derived initially from the effective current downstream proxy key (not an upstream account key), but its hash/storage is independent. Remote first-login requires that initial key **and** an out-of-band independent one-time initialization code, then *only* a forced new-password operation. Before that succeeds all other management access fails. A separate safe bootstrap flow is required when the client key is empty; empty password/default-open management is forbidden. Store salted password verifier and initialized state under DATA_DIR through existing same-directory atomic writes; never return hash, password, bootstrap code or raw sessions in APIs/logs. Normal upgrade and restart reuse the stored verifier; loss/reset goes through an explicit trusted recovery procedure, not implicit re-derivation from the API key.

Use secure, HttpOnly, same-origin/SameSite session cookies, bounded lifetime and login throttling; logout/change-password revokes active sessions. Unsafe methods need CSRF/Origin protection. Do not cache sensitive management data. Remote TLS termination is accepted only with the matching public HTTPS Origin/Host, a private peer and an independent reverse-proxy token placed by a trusted proxy replacing client-supplied Headers; private-network peers alone cannot attest TLS. Concurrent failures are rechecked after body admission before scrypt. A login overlay covers drawers and prior sensitive content opaquely when the session expires. The browser `api()` keeps feature-owned request state while switching from localStorage key to cookie session. Old `cps_key` must be removed, not copied to a new persistent credential. Password change and proxy API key rotation are independent operations.

## Risk/compatibility

This is a contract-breaking management authentication migration; existing remote admin scripts must adopt login/session authentication or an intentionally separate, scoped admin credential if explicitly requested later. No invisible legacy key bypass. Production raw-body logging cannot be enabled during migration, pre-first-change state or rollback to the old management guard. Manual operation/deployment needs a rehearsed rollback avoiding lockout while not exposing raw logs. `admin-auth.json` is sensitive operator state and must be backed up alongside config/metadata; an old release restores the old shared-key management behavior and therefore cannot safely serve raw detail data. Existing production data is not opened during local tests. Local focused/full tests passed, but real-browser keyboard/narrow-width and actual reverse-proxy TLS behavior remain unverified.
