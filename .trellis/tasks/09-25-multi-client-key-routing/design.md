# Multi-key routing design (planning)

## Data and migration

One config owner in `server.js`: retain `config.proxyKey` as the **sole stored secret for stable ID `legacy`** (effective `PROXY_KEY` env continues to override it at startup), and add bounded `config.clientKeys` for *additional* `{id,name,key}` records only; reject an extra record with ID `legacy`. A single helper builds the effective inventory so there is no duplicate mutable legacy secret or second authentication path. Strict authenticated create/rotate/delete actions for additional keys live under the current security boundary; keep existing `GET/POST /api/security.proxyKey` compatibility for old clients, with only additional-key listings masked and new generated secrets returned once on create/rotation. Store extra keys under the existing private operator `config.json` policy; future encryption/at-rest storage is not implied. Stable key ID (not raw secret) is `accounts[].clientKeyId`; startup/old full-list save defaults it to `legacy` for existing accounts, preserving previous owner by stable account ID. Validate complete inventory plus every account reference before atomic `config.json` replacement; missing config uses defaults, malformed operator JSON never overwritten. Bound number/length, reject duplicate secrets/IDs and any new key equal to the current admin password, check every effective key against initialized admin verifier at startup, and prevent deleting a key still owning accounts. Empty legacy key stays an explicit open legacy mode; creating an additional key while a legacy-owned account is still anonymous is rejected until the administrator explicitly configures a nonempty legacy key, to prevent silently disabling all old clients or giving anonymous callers new-key accounts. No accidental anonymous access to newly keyed accounts. `PROXY_KEY` env startup override has explicit source/rotation warning and rollback test.

## Request lifecycle

At model-route auth resolve a request-local stable key ID. Pass the ID into `handleChat()` / `acquireAccountLease()` and filter candidate accounts **before** hard eligibility, mode ranking, active-account fallback, cache-pool selection/growth/standby and waits. For the `single` mode use legacy active account when it belongs to the key; otherwise deterministic first owned eligible account (not a foreign active index). Account-health, quota and per-account RPM owners remain account-ID keyed; Provider attempt retries remain on the chosen owner account, and only the documented pre-stream removal can replace it *inside the same key scope*. Calculate empty-pool 503 versus local busy 429 from scoped candidates, not global `enabledAccounts().length`. Stateful binding `Map<fingerprint,...>` needs key-scoped HMAC namespace or `(keyId,fingerprint)` and eligible-owner check; invalidated on owner reassignment, deletion or key revocation, including provisional tokens. Ensure catalog/model routes do not select an account outside the authenticated client's pool; admin probes/tests remain explicit admin capabilities. Do not log raw client keys or supply downstream Authorization to upstream.

## Secret and UI boundary

Reuse the existing independent admin session/CSRF. Audit redactors (`boundedProviderNote`, `safeReason`, detailed root seeds and other secret allowlists) for **all** configured client key values; avoid loop-cost surprises by bounded inventories. No extra key material may appear in ordinary logs or sanitized diagnostic metadata/Headers; deliberate default-off raw *body* capture remains its separately authorized exception and cannot promise removal of user-embedded secret text. The existing security panel and `ACCS` draft add key labels/owner selectors; `collectAccounts()` sends complete objects. Key create/rotate/revoke changes are separate confirmed writes that reload server-accepted state; an attached-account delete returns conflict without modifying either side. Clear/mask newly shown credentials on nav or dismiss. The legacy `GET /api/security.proxyKey` remains admin-only and needs deliberate backwards-compat regression; no new plaintext in stats/meta/logs/public `api/meta`.

## Rollout and rollback

Run migrated copies of legacy config (including env override and no-key case) and old-image rollback tests against private synthetic `DATA_DIR`. Atomic writes cannot rescue an old binary unable to parse a new schema: document a reversible copy and cutover precondition. No production key inspection/rotation without separate authorization. Tests should assert zero foreign upstream attempts under racing cancellation/retries and old POST round trips.
