# Monthly quota statistics — planning draft

## Source and calculation

The existing validated `accountQuotas.snapshot.limits` contains `five_hour`, `weekly`, `monthly` percentUsed and optional resetsAt; no authoritative dollar balance exists. The user's screenshot supplies *community reference caps* $10/$25/$50 per account, not Cline's guarantee. The operator confirms the **current whole pool** is the same Cline Pass subscription with a $50 monthly reference cap; no per-account plan/eligibility field is added. This is a pool-level display assumption, not an upstream billing fact. For an eligible account, calculate each reference remaining `cap × (100 - percentUsed)/100`; monthly total sums only valid monthly remains, while currently usable reference total sums `min(5h_remaining, weekly_remaining, monthly_remaining)` per account with all three valid windows. Never take min(percent) and multiply by $50. Display original percents, reset times, captured/fetched time, separate inclusion/exclusion counts and separately labelled estimates.

Keep known 0 and 100 distinct from missing. A disabled/unconfigured/failed/stale snapshot enters neither sum; a **fresh partial snapshot with a valid monthly window** may enter the monthly-only sum but not the three-window immediate sum. The existing `quotaProjection()` marks partial snapshots `unknown` for routing; the UI must assess the monthly-only diagnostic freshness independently from its existing `fetchedAt`, `lastSuccessAt`, `lastAttemptAt`, `errorCategory` and 15-minute freshness window. It must not turn a partial routing snapshot fresh. Existing quota job, refresh controller/generation, account list and statistics endpoint own data. Do not add another remote quota endpoint, persisted plan field or infer token balances. The UI calls all $ amounts community estimates under the operator-confirmed same-plan assumption, never actual balance.

## Compatibility

Retain existing three-window quota columns and quota-pool routing semantics; changing aggregate display alone must not make a stale snapshot fresh. Operator wording distinguishes monthly remaining from immediate 3-window bottleneck. Show distinct included/excluded counts for monthly and immediate summaries. The four existing forecast horizons may show both totals, restoring a window's reference cap only when its validated reset is strictly after `generatedAt` and no later than the target; otherwise conservatively carry its current remaining amount and label incomplete reset coverage. Future values assume no new consumption and are lower-bound predictions, not guaranteed usable balance. Once an account with another plan is introduced, the pool-level assumption must be revisited before displaying a combined $ estimate.
