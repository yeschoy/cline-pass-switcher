# Prior performance evidence and task-specific gaps (read-only, 2026-09-27)

## Reuse instead of rediscovery

Archived `.trellis/tasks/archive/2026-09/09-25-whole-service-performance/research/{results,worst-cases,remaining-flows,statistics-read-results}.md` already profiles almost the entire service on local arm64/Node v26.8.1 with temporary DATA_DIR and mock peers. It is not live telemetry. Its scripts under the same `research/` tree are reusable after reviewing their input/cleanup safety and current-HEAD compatibility; no production corpus or paid endpoint is needed.

- Large synthetic 1,200-minute metadata: baseline one terminal atomic JSON rewrite spent mean 12.62 ms stringify + 2.87 ms temp write + 0.32 ms rename. Existing compact-meta work reduced same synthetic stringify to mean 8.64 ms and small-chat dense-history median ~19.82 to ~14.35 ms in one paired run. `server.js:114–125,192–197,2937` still synchronously serializes and writes metadata on terminal completion. This remains a candidate under **current** high-cardinality traffic but is not a new discovery or license to drop per-request durability.
- One 10-account sticky+healthSort, 12-concurrent, maxConcurrent=1 mock case observed ~1,448 `successHealthProjection()` calls and ~29–34 ms total across the batch; 30 metadata serializations were more expensive. It did not test a load+health strategy, different account counts or sustained throughput.
- Opt-in full sanitized five 5 MiB chats had p50 ~29–30 ms, one p95 ~328–334 ms, loop maximum ~302–311 ms and safe capture-budget omissions; there is no isolated `raw-full` comparative run in that whole-service report. The separate `.trellis/tasks/09-26-production-raw-body-enablement/research/target-load-20260926.md` reported an isolated two-concurrent ~34 MiB raw-full success case under 2 GiB with a capture-budget drop, sampled peak cgroup ~1.02 GB and max loop ~149 ms; overlap and sustained headroom were not proved. Avoid interpreting these as production safe concurrency.
- Dense 1200-bucket × 4-model × 3-Provider `/api/statistics` GET p50 ~45.7 ms; a single-pass prototype saved only ~2 ms within normal run variance and was not shipped. This is a management read, not the per-chat hot path.
- Cold model catalog synthetic 12 parallel reads caused 12 mock upstream fetches; warm fetches zero. This is a real cold stampede under that fixture but frequency/production effect unknown. Ordinary rare-filter query near cap was ~77–78 ms p50; first page ~3 ms. Detail startup inventory (5,000 roots) ~1.3 s while chat remained available. These are distinct admin/startup candidates, not necessarily high-concurrency chat bottlenecks.
- HTTP CONNECT/SOCKS5/direct serial local tests reused one upstream socket over 24 chats; replacing transport or adding a proxy path has no evidence of benefit. Large-body retries, raw diagnostics, simultaneous TLS proxy pressure, many-account ranking, sustained load and representative 429 distribution remain open.

2. Report source attribution and overlapping timings without adding nested durations.
3. Use prior harness where valid, document the exact revision and differential semantics, clean disposable fixtures on exit, and avoid reproducing all archived baselines. Rank by frequency × measured cost × model-traffic impact; recommend only changes with evidence and boundary-preserving tests. If a desired endpoint cannot be measured, name the missing anonymized metric rather than claiming a speedup.
