# Cross-deliverable design map (planning)

## Boundaries and order

The parent is coordination-only. Because whole-program speed is the user's central concern, review the **performance child first**, then pricing, UI and multi-key sequentially (no concurrent writers on `server.js`). The performance child owns current-HEAD whole-flow measurement and evidence-backed fixes; later feature children must rerun relevant baseline cases, and parent integration repeats on the fully changed tree. Pricing and UI share existing statistics / read-only browser projections: freeze a new reference price version before final UI wording. Multi-key owns authentication, config/account normalization and account-selection/lease; its scheduling overhead is compared with the same synthetic benchmark after implementation. Do not compare different schema/config workloads as if identical. Each independent commit remains rollback-capable.

## Contract intersections

- New price owner uses the current 12-model ClinePass reference table plus the user-designated DeepSeek direct price page for V4 Pro/V4.1 Flash peak/off-peak rows; old screenshot/old v1 amounts remain frozen. Valuation uses explicit final-success input/output/cached-read Token to produce a labelled reference consumption equivalent in USD, **never** a real ClinePass subscription bill or account remaining balance. Without a verified tier/holiday fact DeepSeek displays a peak/off-peak interval. A tariff row may be visible even when Cached Write/context evidence prevents complete valuation. The account monthly-reference forecast independently remains `$50 × (100 − monthly.percentUsed)/100` per eligible account; no model-cost subtraction. Use existing versioned statistic cells and retention/overflow coverage; no automated paid price fetch, new billing store or backfill.
- The model tab uses one final-request sample per resolved model. The channel tab uses `(resolved model, named Provider)` real attempt health samples and final-success attributed usage (plus explicit unknown-Provider usage). The API already projects these; do not make a new statistics store or silently sum failed retries into usage. Move verbose version and coverage explanation into an accessible expandable detail tied to its row; preserve source link and effective-date uncertainty.
- Client key authentication yields an internal stable key ID, not a raw key attached to request logs/statistics/body. Filter candidates by that key ID **before** any legacy/pipeline/cache pool/stateful-binding ranking, waiting, standby expansion or pre-stream replacement. A shared session fingerprint must not reuse a binding from another key; scope its in-memory identity and invalidate on ownership changes. Account `.key` stays the upstream credential and must never be confused with downstream key ID. `activeAccount` single mode needs a deterministic in-scope fallback if global active belongs to another key; empty in-scope pool fails closed without borrowing. Management probes/tests using explicit account IDs remain independently admin-authorized, not client-key-routed.
- Preserve the old `proxyKey` and environment `PROXY_KEY` startup override as an explicit *legacy key* compatibility boundary. The multi-key child design uses one stored legacy secret plus additional key records, and migrates stable account owner IDs without duplicate mutable legacy secret owners. An empty legacy key currently means open model traffic; retain it for a legacy installation until an admin explicitly configures authenticated keys, after which unknown credentials must fail closed. Account full-list saves and key management must validate foreign IDs, deletion with attached accounts, rotation, re-login, admin-password equality and persistence before mutation. Never turn a client key into an administrator login path. New secrets should be shown only when created/rotated, with admin UI labels and safe masked projections; do not print or fixture real keys. Existing older clients may depend on `/api/security.proxyKey` and need an explicit compatibility test if shape evolves.
- New keys affect all credential scrub lists (`boundedProviderNote`, `safeReason`, diagnostic capture/Headers) and catalog/model routes. User-facing auth failures must not reveal whether a key ID exists. Safe optional bounded key ID/name projections need cross-layer audit: metadata, JSONL, detailed manifests, statistics, config APIs, public meta and source. An in-flight request may finish on its already leased account when an admin rotates a key, while *new* admission immediately uses the new inventory; no replay or cross-key reassignment.

## Performance experiment and rollback

Treat startup, request parsing/auth, scheduling, upstream transport/retries/SSE, statistics/persistence, ordinary/detailed diagnostics, quota jobs, management API and browser rendering as separate performance surfaces. `research/perf-*.md` records code-grounded candidates; `research/local-latency-results.md` provides a narrow current-HEAD loopback measurement: cloning 1200 valid minute buckets expanded metadata to 13.39 MB and moved small-chat p50 from ~2 ms to ~18–20 ms, statistics GET p50 from ~1.5–1.8 ms to ~14–23 ms. This is a reproducible **correlation**, not proof that `pruneStatistics()` or `saveMeta()` individually dominates; detailed CPU/I/O attribution remains required. Also probe large-body multi-retry cloning, large-account ranking/wait storms, cold catalog fetch, diagnostics mode, cold startup and management/browser redraw rather than tuning only for aggregate RPM. Use isolated temp `DATA_DIR`, local mock, representative bodies and actual browser traces for UI. Track frequency × cost, median/tail latency, CPU/loop delay, RSS/heap, I/O/queue drops, fairness/limits and cold vs warm. 300 RPM is one optional throughput sample, not the target to optimize at all costs. Retain atomic durable truth and fail-open traffic; no generic queue, second store, weakening stats coverage or blanket disable of logs. Rerun identical workloads and failure/restart/SSE cancellation tests. No production load, privileged credentials, raw-body enablement or release operations without separate authorization.
