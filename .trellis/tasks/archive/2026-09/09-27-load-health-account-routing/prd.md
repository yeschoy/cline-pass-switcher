# 无粘性负载与健康度联合调度

## Goal

新增可选账号调度模式，使没有会话粘性约束的并发请求在健康账号之间主动分流；另将整个池无法接单时的等待时间与粘性首选/绑定账号等待分开配置。

## Background

- 用户担心现有健康排序高并发会倾斜到同一账号，引发 429，并明确要求“低负载＋健康度高”的无粘性新模式；进一步关心 `maxConcurrent=6` 时第七个会话是否仍会打到同号。这里的限制按同时在途请求而非累计/唯一会话计数（`server.js` 1431–1463）。用户又要求新增“账号池都满情况下的等待时间”配置，明确有别于粘性首选/绑定账号等待；当前 `concurrencyWaitMs` 被两者复用（`server.js` 1533–1569、1813–1997）。
- 当前健康分层在有评分时按成功率降序；`maxConcurrent`/`maxRpm` 主要作为准入约束；已有 `least-connections` 等账号模式和 `accountPipeline.healthSort`。具体组合、重试和会话条件需继续追踪（`server.js` 1533–1569、1610–1650、1917–1997）。

## Requirements

- 新调度行为必须显式可选，旧配置和旧模式保持原语义；保守限定在未开启任何粘性的账号池请求，不改变粘性配置中首次未命中绑定、已有绑定、HRW 的选号。新增池等待字段必须在缺失时继承既有 `concurrencyWaitMs`，不能仅因升级改变旧配置的超时、溢出和本地 429 时机。
- 选号兼顾可用资格、当前负载与健康度；健康样本缺失不可当成 0，负载要与有限/无限 `maxConcurrent`、RPM 等现有准入事实一致，不能仅靠健康率最高的账号吸收所有空闲请求。
- 新池等待仅在同一客户端密钥归属的当前可参与候选全都设置了有限 `maxConcurrent` 且均因**并发满**不可准入、RPM 仍有余量时使用；首选账号满但其他有容量时，不触发池满等待，应依据选定模式的既有粘性/溢出契约处理。RPM-only/混合阻塞继续既有等待与 Retry-After，容量释放可提前唤醒；不得新增无界队列或将流式输出后的失败重试到另一账号。
- 不突破客户端密钥账号池、禁用、隔离、额度 reserve、限流与 Provider 重试仍固定在已租账号等约束；上游 429 并非总能被本地负载分流避免。
- 管理 API、持久化校验/迁移、控制台完整草稿与展示、日志安全投影、操作者文档和规格同步更新。

## Acceptance criteria

- [ ] 本地 mock 覆盖 `maxConcurrent=6` 的第七个**同时在途请求**不能租到该号、前六个结束后可再次租到；无粘性与粘性绑定命中/未命中分别覆盖等待、其他号可用和全池饱和/RPM 耗尽的现有错误语义。多个健康、可用账号在无粘性并发下有可解释的分流；不以“429 一定为 0”作为验收。
- [ ] 已绑定/显式粘性请求与旧模式的选号、等待、溢出、重试、租约释放行为不回归。
- [ ] 新池等待字段在无字段旧配置时保留旧超时和 Retry-After，合法值 round-trip、非法配置拒绝且不持久化；单账号、粘性首选阻塞但池有空闲、全池并发满、RPM 耗尽/混合阻塞、动态扩容及等待提前唤醒均有定向测试。
- [ ] 管理 API 和前端完整草稿与新模式及池等待设置一致；相关集成/前端测试覆盖。

## Scope boundary for review

- 新调度仅用于**关闭粘性**的账号池；未获明确同意前，不改写粘性配置首次会话绑定选号。
- 已确认新增池等待仅覆盖纯并发全满；RPM-only/混合阻塞继续原配置。若两个计时条件先后出现，单次请求应有有界、可解释的总等待，不能意外叠加两段超时。
