# 增强统计、日志与错误规则体验

## Goal

让运维人员能够快速判断每个模型和账号的缓存效果，正确理解模型上游发现状态，以低开销保留可查询的普通诊断日志，并通过易用且安全的界面管理账号错误规则和额度信息。

## Background

- 模型表当前把 `meta.upstreams.length` 直接显示为“上游数”。截图中的模型已经探测到 Vercel 管道、canonical model 和最近实际 provider，但 planner 列表构造遗漏 `finalProvider`，且渠道 harvest 可能无法解析对象形态的错误包，因此 `0` 只表示“发现列表为空”，不表示模型没有上游（`public/index.html:450-465`、`server.js:890-925`、`server.js:952-967`）。
- 现有统计只持久化全局和按账号聚合，没有按模型聚合。缓存请求命中率已经定义为明确报告缓存字段的请求中 `cachedTokens > 0` 的比例；缓存 Token 占比是缓存输入 Token / 输入 Token（`server.js:1100-1124`、`server.js:1148-1178`、`server.js:2333-2337`）。
- 普通 `JsonlLogStore` 仍在构造、追加、每 100 次整理、组合容量检查和查询时执行同步语料扫描。既有生产证据显示约 10.7 MiB 普通日志曾在监听前造成明显冷启动阻塞；本地临时基准中 5,000 条追加耗时约 3.6 秒。详细日志存储已经通过独立任务做过增量索引优化，本次剩余瓶颈是普通请求/错误 JSONL。
- 账号错误规则目前通过一个较小的高级 JSON 文本框编辑；服务端仅支持精确状态码和 `ignore` / `cooldown` / `ban`，尚不支持先前纳入规划的失败响应内容匹配（`public/index.html:237-240`、`server.js:157-174`、`server.js:252-263`）。用户已确认改为“可视化规则表格 + 可折叠高级 JSON”，两者共用同一草稿。
- 额度列同时显示已用和剩余百分比，信息可互相推导，截图确认造成冗余（`public/index.html:1030`）。
- 详细代码与基准证据见 `research/code-performance-findings.md`。

## Requirements

### R1 — 每模型缓存命中率

- 为每个已知/已路由模型维护并展示缓存统计，不得从普通日志临时反算。
- 统计只使用上游明确返回的 usage；缺失/非法缓存字段必须保持“无数据”，明确的 0 必须显示为 0%，不得互相混淆。
- 模型别名请求归入解析后的实际模型，避免同一实际模型被多个别名拆散；API/UI 必须清楚标明统计口径。
- 每个模型只展示最近 24 小时缓存 Token 占比（缓存输入 Token / 输入 Token），不展示请求命中率；同时展示具有成对 input/cache usage 的覆盖请求数，使低样本高比例不会伪装成稳定结论。
- 模型统计不得改变探测元数据、路由配置、账号草稿或普通日志投影。

### R2 — 高性能普通日志

- 优化 `DATA_DIR/logs/requests-*.jsonl` 和 `errors-*.jsonl`；不重做已优化的详细正文日志存储。
- 服务必须先开始监听，再在后台执行一次普通日志索引恢复；恢复期间模型请求与新日志追加正常工作，普通日志查询明确返回安全的 `503 日志初始化中`，不得返回不完整历史数据。
- 服务监听前不得同步读取、解析和重写完整普通日志语料。
- 正常追加热路径不得为每条记录重新枚举/统计全部段，也不得每 100 条重写全部语料；日志维护失败继续 fail-open，不改变模型响应。
- 查询、保留期、记录数上限、100 MiB 请求/错误组合容量、分段、去重、损坏/截断容忍、独立清空和游标行为保持兼容。
- 保持现有严格普通日志投影：不得新增请求/响应正文、Header 值、原始会话、账号备注、代理或凭据。
- 新增可执行的文件系统调用计数与性能回归：初始化完成后，普通追加不得扫描历史语料；同机 5,000 条代表性追加必须至少比当前约 3.6 秒基线快 10 倍，并记录启动、查询、维护和内存证据。绝对耗时只作为报告，不作为跨机器硬门禁。

### R3 — 模型上游发现状态

- “上游数”不得把未发现/解析失败伪装成已知零；UI 应显示“未发现/未知”并提供可操作提示。
- 成功响应中已经观察到的实际 `finalProvider` 必须进入安全的已知候选集合，避免出现“最近实际上游存在但上游数为 0”的自相矛盾状态。
- harvest 应兼容实际的字符串和结构化错误 envelope，但只接受严格 provider slug，不保存原始错误体。
- 探测、测试和校验仍是独立动作；不能因修正显示而声称未校验 provider 已经可钉住。

### R4 — 易用的错误规则面板

- 用可视化规则行支持新增、编辑、删除、排序和校验；状态/内容条件、动作和冷却时长必须使用有标签的原生控件。
- 保留高级 JSON 入口供批量/专家编辑，但可视化与 JSON 必须投影到同一个规则草稿，不能形成两套互相覆盖的状态。
- 继续兼容全部既有精确状态码规则和预设；保存仍走现有完整账号配置边界并由服务端权威校验。
- 纳入失败响应内容匹配：首版只支持大小写不敏感的普通文本包含，可选限定归一化状态码；不支持正则、“不包含”或 JSONPath。
- 内容规则只检查已判定失败的响应（包括 HTTP 200 错误 envelope），按显式顺序首条命中；未命中才回退既有状态码规则，命中的 `ignore` 也是最终动作。
- 内容匹配输入使用完整但有界的规范化错误信息，保留嵌套 `message`、`code`、`type` 等诊断字段；匹配前必须脱敏配置凭据、代理/Header 值及当前请求消息，不能直接扫描或持久化原始响应体。
- 匹配输入、数量、文本长度和冷却时间必须有严格上限；不持久化/显示原始响应体或匹配片段，不泄露凭据、消息或 Header 值。
- 首包后 SSE 不得重放；内容规则只能影响后续账号状态。

### R5 — 额度显示去重

- 账号额度的 5 小时、每周、每月窗口只显示剩余百分比和重置时间，不再同时显示已用百分比。
- 已知 0%/100%、未知、部分、失败、过期和禁用状态语义保持不变。
- 总可用额度预测继续使用相同服务端 `percentUsed` 数据计算，不改变预测算法或路由判断。

### R6 — 账号主表统计摘要（既有任务范围）

- 在账号管理主表按稳定账号 ID 展示最近 24 小时缓存 Token 占比和健康摘要。
- 健康摘要包含状态、可用时的评分、最近 24 小时失败数和累计失败数。
- 缺失覆盖、样本不足、溢出或覆盖不完整必须显示“无数据/数据不足”，不得伪装为 0。
- 统计刷新不得覆盖未保存的账号、批量、抽屉、调度或错误规则草稿。

## Acceptance Criteria

- [x] 每个模型可看到最近 24 小时缓存 Token 占比、明确覆盖样本数和无数据/已知零状态；不显示请求命中率，别名请求归入解析后的模型。
- [x] 模型统计在非流式、流式最终 usage、provider 重试、账号替换、失败和客户端取消路径中保持 exactly-once。
- [x] 截图所示模型不再出现“已知最近实际上游但上游数 0”的误导；发现失败与真实候选数量可区分。
- [x] 服务在普通日志后台恢复前已可接受模型流量；恢复期间日志 API 返回明确 503，完成后历史与新记录均完整可查。
- [x] 普通日志启动/追加不执行历史语料全扫或周期性全量重写；合成基准和文件系统调用断言证明改进，现有查询/保留/安全契约全部通过。
- [x] 错误规则可以完全通过可视化面板管理；高级 JSON、预设和可视规则往返不丢字段、不覆盖其他账号草稿。
- [x] 旧状态码规则无需迁移即可使用；内容规则的非流式、首包前 SSE、首包后 SSE、优先级、回退和严格校验有可执行测试。
- [x] 额度窗口只显示剩余百分比与重置时间；已知边界值和未知/过期状态仍准确。
- [x] 账号主表统计按稳定 ID 关联，重命名、重复名称、搜索、草稿编辑和刷新不会串行或丢失状态。
- [ ] 服务端、普通日志、生产脚本 VM/UI 和完整项目门禁已通过；真实浏览器交互因本机 browser binary/Accessibility 基础设施阻塞而未验证。

## Out of Scope

- 不修改详细日志正文捕获/脱敏协议或其 7 天/1 GiB 存储。
- 不引入数据库、前端框架、构建工具或第三方规则引擎。
- 不改变健康评分权重、缓存池调度算法、额度预测算法或 provider 选择策略。
- 不保存原始响应体作为规则命中证据。
- 本任务不包含生产部署或生产数据清理。
