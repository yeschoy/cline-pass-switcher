# Account quota exhaustion protection — planning draft

## Signals and state

Keep this policy distinct from configurable errorRules while reusing the existing normalized bounded failure facts and **existing quota job owner**. An actual pre-output upstream HTTP 429 with explicit account/subscription quota evidence and a match in the bounded/redacted failure text (not a generic/provider 429, local RPM block, HTTP-200 success, post-start SSE output or cancellation) initiates a deduplicated, backoff-respecting forced refresh for that same account. One process-local provisional hold, capped in duration even when the quota API fails or queues behind other work, prevents a concurrent storm while verification is pending. Its expiry does not invent a persistent ban or create a permanent wait. The signal records only a safe account ID, trigger time and quota success version; no raw body or Header. Preserve the original upstream response/status and existing retry/error rule decisions.

The new permanent *monthly* ban requires all three signals on the same account: actual matching 429 status, matching bounded/redacted content, and a **successful new** monthly snapshot from the existing quota job after the trigger with reference remaining strictly `< $0.20` by default. The global `quotaProtection.monthlyThresholdUsd` is a finite two-decimal amount in $0.01–$50.00, default $0.20; an older complete account save omitting it retains the server value. Validate before mutation/persistence. Compare at the exact $0.20 equality boundary without binary-float rounding making equality appear below threshold. A monthly-only successful snapshot may establish the month fact while remaining routing-unknown; a failed/old/stale/partial-without-month snapshot cannot. Persist a separate manual-release monthly ban enum/time under existing `META.accountStates[id]`, independent of ordinary rule cooldown and existing known-100 disposition. Neither timeout, reset, refresh, restart, quota-pool changes, key/proxy rotation nor ordinary rule recovery clears it; account deletion prunes it, and a distinct authenticated exact-ID admin action clears only it. The ban is checked before leasing on all account-selection paths regardless of low-slot cache-pool enablement.

5h/week window exhaustion has a separate automatic temporary block. A freshly confirmed 100%-used 5h or weekly window records every exhausted window, independent of low-slot routing; an available 5h with exhausted week is still blocked. A persisted confirmed short-window block can outlive a network outage, but incoming requests fail fast rather than waiting indefinitely. Recheck near the earliest valid future reset among exhausted windows via the existing quota timer; absent/past times use bounded backoff. Each new success recomputes all three windows; automatic reentry requires a **new full three-window** snapshot with each `percentUsed < 100`, positive recovery of each held window relative to the original exhausted observation, and no monthly manual ban. A partial/failed snapshot or a timer alone never unlocks. If an error cannot identify a window and no fresh window is 100%, keep only the expiring provisional hold. Reuse the existing `quotaJobs` dedupe/queue and extend its owner/timer eligibility for this policy even when optional quota-pool routing is off; do not use a fake browser page token or a second network scheduler. Keep credential/proxy/generation fencing; a key/proxy rotation invalidates only pending/short-window evidence, never a stable-ID manual ban.

## Management and compatibility

Expose safe per-account reason/state/next check, threshold settings and an explicit recovery action in current account/statistics projections. Store only bounded booleans/enums/timestamps/threshold, not raw error text or monthly dollar history. `GET/POST /api/accounts` projects/round-trips the global threshold and preserves it for older-client omission; `POST /api/accounts/quota-recover` accepts exactly `{ id: <stable existing account ID> }`, requires the independent admin session/CSRF, and clears only the monthly ban after explicit browser confirmation warning of possible repeat failures. The existing `/api/accounts/recover` clears rule fields only. Full account saves cannot unknowingly reset a manual ban (including key/proxy rotation); invalid persisted state must fail startup without overwriting bytes. UI read/write stays under existing `ACCS` draft/snapshot owner, with server-authoritative validation and accepted-state reload. No production fetch is part of planning/testing.
