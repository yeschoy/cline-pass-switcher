# Synthetic full-state backup and compatible-image rollback — 2026-09-26

**Boundary:** deployment was requested, but the live switch remained blocked. This rehearsal used a fresh, sentinel-marked root-private **synthetic-only** DATA_DIR and synthetic Compose/env/gateway/deployment-record sidecars on the production host. It did **not** copy production logs/bodies/credentials or replace production files, containers, Compose, gateway, memory or raw settings. `research/isolated-full-rollback.py` is intentionally limited to 128 entries, 64 KiB per non-raw file and 2 MiB non-raw bytes; it is **not** a production backup/rollback tool.

## Read-only scale preflight

The live DATA_DIR contained approximately **35,816 regular files, 7,277 directories and 927,471,583 bytes**, with zero observed symlinks/special entries and zero regular raw-group files, at the bounded scan time. The filesystem reported ~419 GB free and both exact image IDs remained present. These facts do not freeze future operator writes or prove future raw backup exclusion. A real complete rollback backup is materially larger than the previous config/metadata/admin trio; none was created in this rehearsal.

## Actual isolated sequence

1. The synthetic v1 source was derived only from the prior synthetic mock fixture: one account, no `clientKeys` or `clientKeyId`, raw=false, valid synthetic admin state/metadata, tiny legacy/log markers, plus a **163,840-byte synthetic raw marker and a symlink inside raw/**. Four synthetic sidecars represented Compose, env, gateway and deployment record. Root and child directories were mode 0700; no live DATA_DIR path was accepted by the helper.
2. An exclusive private v1 backup copied the complete **non-raw** synthetic DATA_DIR and sidecars with rsync, using `--exclude=/detailed-logs/raw/***`. It verified every selected path, file bytes, owner/group and mode, including empty directories. The raw directory **and descendants** were absent from the backup and candidate-working copy, while legacy/log markers and all sidecars remained. The helper rejects unmarked/wrong/symlink/hardlink paths and cannot seal interrupted staging. Independent review found that an initial unframed tree digest was unsafe across adjacent file boundaries; the helper now hashes each file with an explicit length and independent SHA-256, checks sensitive fixture modes/marked-root owner, and the **entire sequence was repeated in a fresh synthetic root** with this corrected version. The disposable local test includes a cross-file boundary counterexample plus wrong-hash/current-drift no-op cases. These are not a production write fence.
3. Exact committed-main candidate image `sha256:f7c45edc2ccba0eab83baea36db65ffe70e4a19fd4c1b275b8fa6565f4e765bd` started against only the synthetic working copy with `--network none`, 2 GiB, UID/GID 1000:1000, read-only root, dropped capabilities and tmpfs. `/api/meta` returned 200, zero restarts/OOM; the sole account acquired `clientKeyId=legacy`, `clientKeys` was present, raw remained false and the service-created `raw/` directory was **empty**. It was stopped before snapshotting. The post-migration v2 copy was sealed separately with the corrected synthetic tree digest; its value was used only inside private rehearsal state and is not a production hash prediction.
4. A deliberately wrong expected digest returned failure **without creating the restore destination**. The correct hash restored v1 to a *new* isolated path, leaving v2 working and post-v2 copies separate. Config, metadata, admin, synthetic legacy marker and all four sidecars matched the v1 backup byte-for-byte; raw remained absent. The exact old production image `sha256:0bd1deaefb04b6c2c3f1e3417eddc07b3fc6dd6398212ff98e6a783c3c62100c` then started on **only** that restored v1 state with `--network none`, 512 MiB and the same hardening: `/api/meta` 200, synthetic administrator login 200 and authenticated detail-settings GET 200; unauthenticated settings GET 401. Zero restarts/OOM, v1 config bytes unchanged, raw=false. The old image was never started on writable v2. It was stopped after the check. The 200/401 status observations came from a separate isolated container execution, not from the Python backup helper; `--network none` does not prove actual gateway ingress isolation.

## Disposition and unresolved gates

This demonstrates the **shape** of a code-only raw-off rollback on a small quiet synthetic tree, not full production readiness. The helper cannot handle live-scale file counts/sizes and does not atomically switch the real DATA_DIR/Compose or establish a concurrent administrator-write fence. A failed copy may leave private **unaccepted** partial staging; wrong-hash no-op covers only the pre-restore boundary. The candidate network-none startup can make quota-attempt metadata writes, so the copied-data metadata hash is not a stable migration-only prediction. There is no complete root-private backup/restore proof for the ~927 MB live corpus, no tested live gateway/old-image ingress isolation, no post-upgrade operator-save preservation under actual cutover, and no administrator-only browser acceptance against the actual isolated service. The previous release's config-hash mismatch remains separately pending. Raw-on additionally needs external backup exclusion or independent 48h expiry and reviewed cgroup headroom.

**No production deploy occurred.** Final read-only post-check found live Compose/config/deployment hashes unchanged; the old image remained running/healthy at 512 MiB, no raw-ready flag, zero restarts/OOM. The synthetic staging is retained privately pending explicit cleanup consent. A production-scale private backup and exact release rollback must receive a separate, reviewed cutover procedure and privacy/retention decision before live mutation.
