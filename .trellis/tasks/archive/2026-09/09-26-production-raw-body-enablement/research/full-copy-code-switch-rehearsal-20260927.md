## What remains unsafe to claim

This demonstrates a *stopped-old → fresh full v1 backup → exact new image → preserve v2 → restore v1 before old start* shape on isolated copies. It does **not** prove a bounded actual production outage or an independently supervised **stop/start** recovery after SSH/coordinator loss. The backup-only persistent **unpause** watchdog cannot restart a stopped old service and must never automatically restart an old image on migrated v2. A combined live window therefore needs a reviewed stop-first recovery owner that restarts the same old container only while the current data is independently proved compatible v1, and blocks/reports on ambiguous or v2 bytes. It also needs a current full-v1 copied-data migration prediction, exact release-tree/image/source recheck, client traffic drain/ingress and non-container writer fence, authoritative sidecars, a fresh rollback snapshot and positive administrator/gateway/internal checks. Preserve post-switch v2 state before any rollback; an unmatched hash or later operator save requires a separate recovery decision, not blind restore.

After this isolated test, production remained on the same healthy old image, restart 0/OOM false, 512 MiB, original Compose/config hashes and raw=false. The new code image is built but **not deployed**. No raw-on resource/privacy/browser gate was accepted.
