## Planning/code conflicts or ambiguities to resolve before implementation (do not silently change requirements)

1. **Legacy env precedence is not continuously pinned.** Nonblank env key wins *startup*, but `POST /api/security` immediately replaces runtime `PROXY_KEY` and may persist it (`:4973-4984`). Design/UI wording `env-pinned legacy key precedence` suggests pinning beyond startup; current compatibility is startup-only. Clarify desired in-process save behavior/rollback and test it explicitly, rather than describing current env as immutable.
2. **Model listing is not a pure global constant when catalog exposure is on.** `GET /models` aliases call `catalog()` and use global `pickAccount()`, possibly a synthetic `apiKey` account when pool empty (`:1933-1938,4555-4559,5036-5042`). Scoped auth must protect that upstream fetch; the static union may still enumerate account-specific IDs / aliases, so decide whether pool scope applies to visible IDs as well as upstream calls. `/api/models` is independent admin-only and may continue global catalog/explicit account behavior.
3. **One global cache target, global session binding and global capacity counters.** `META.cachePoolTargetSize` is a single shared grow-only target, not per-key; merely filtering `enabledAccounts()` before one selector but allowing internal re-reads to use global state will leak. Design says reuse existing owner, but multi-pool target semantics at the same configured size/max need a deterministic acceptance contract (e.g. shared numeric target applied separately to each key's derived active set); avoid silently persisting per-key targets.
4. **Strict schema is mixed with legacy permissiveness.** Existing `POST /api/security` coerces input/echoes legacy secret, `POST /api/accounts` accepts missing ID on new rows and name fallback and omitted fields; do not inadvertently redesign old shapes while adding strict additional-key and owner validation. `POST /api/accounts` currently mutates config/runtime before both writes, unlike candidate-first atomic changes proposed for keys; ensure invalid owner/duplicate/key deletion fails *before* mutation and failed writes don't leave mismatched key inventory/account ownership.
5. **`legacy` is already used as a synthetic fallback *account ID*** in `pickAccount()`. Proposed key-owner ID `legacy` is a different namespace; ensure no accidental join against account IDs. Startup `CLINE_PASS_KEY` insertion happens after normalization and is not persisted until another save; owner must be explicitly assigned there too.
6. **Design's redaction and secrecy wording needs a precise exception.** The existing admin `GET/POST /api/security` intentionally returns the original plaintext key. "No new secret in normal lists" is consistent with that exception, but new additional-key API must never echo existing additional secrets outside one-time creation/rotation; redaction budget may be exhausted by a large key inventory combined with 128 account custom Headers (`DetailRedactor` max 256 seeds / 64 KiB). Bound inventory with existing budget in mind, then fail closed/safely omit detail if exhausted.
