## Boundary and operational implication

The strict old validator in `HEAD:server.js` accepts six-key v1 price snapshots only; current `server.js` adds seven-key v2 snapshots and freezes request-time valuation cells. Rollback to the previous binary therefore requires a **pre-upgrade private data backup** (including relevant config/metadata/admin state when present) and a fenced restore decision, while separately preserving the latest v2 data and any post-upgrade operator writes. Merely removing the v2 entry from the newest metadata is neither a validated migration nor a lossless rollback. This rehearsal has no administrator login/API-projection, Docker image, target runtime, concurrent operator write, production data or deployment verification; a separately authorized rollout needs its own copied-data hardening/rollback gate before switching.
