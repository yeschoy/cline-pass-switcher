# 会话复用上次成功渠道

## Goal

在当前项目的账号先选、渠道重试与已有会话身份机制上，使同一会话的后续请求优先使用上次成功 HTTP attempt 指定的渠道，减少重复试错并争取上游缓存连续性；按用户选择沿用 Go 版「计划渠道记忆」语义，但明确它不证明上游实际命中。

## Confirmed facts

- 用户要求“新增 go 版本的会话渠道复用，就是复用该会话上次的渠道”。
- 当前账号亲和可使用 HMAC 身份和条件化 session binding，但渠道计划仅按配置来源顺序或全局 Provider-model 健康率排序；Go 版只在上次尝试的渠道仍属于候选时前置它，记住的是 planned `attempt.Upstream` 而非已证实的 actual Provider。
- 源码比较与风险见父任务 `research/upstream-pinning-comparison.md`；本子任务已获批准并完成本地业务代码实现；定期探测子任务及真实上游/部署仍未获批准。

## Requirements

- 仅在同 client-key owner、同 resolved model 且客户端提供**明确对话/父线程标识**（如 `prompt_cache_key`、可信会话/父线程 ID）时复用渠道；仅凭开头消息 HMAC 推测出的 fallback 身份不启用新增渠道复用。不得保存原始会话、Header、正文或密钥。
- 记忆不能绕过当前账号专属 `perModel` 完整覆盖、已配置优先/排除、Provider 冷却/硬隔离、定期探测对该账号的自动避开、现有账号绑定、lease/RPM/取消及重试上限。暂被自动避开时不优先；若以后恢复且偏好尚在 60 分钟有效期内，可再次优先。
- 原账号暂时不可用而换账号时，若新账号自己的完整 `perModel` 路由仍允许已记忆渠道，则继续优先；否则按新账号现有顺序，绝不越过 owner/人工排除/硬隔离。已记忆的渠道失效/不在本次候选中时，回到当前请求的正常渠道顺序；流式请求中途失败或客户端取消不应建立“成功渠道”。
- 用户选择 **A：成功后记本次请求指定的渠道**，即使实际渠道未知或报告不一致也可复用；只作为下一轮候选顺序偏好，绝不能标记为“实际渠道命中”或“缓存命中”。设计须兼容路由元数据缺失、上游忽略 pin、重试后成功、账号更换、配置变更、并发、重启、过期的行为。
- 会话渠道复用默认开启；偏好默认成功后滑动保留 **60 分钟**，重启清空（用户确认）；仅影响下一轮渠道排序，不改变持久人工路由配置。保持可回退；使用临时 `DATA_DIR` 与本地 mock 覆盖跨会话/owner/model 隔离与 SSE 边界，不调用付费真实上游。

## Acceptance Criteria

- [x] 同 owner/会话/模型先 A 失败 B 成功，下一轮若 B 仍被当前账号路由允许则先试 B；账号切换后只有新账号也允许 B 时才继续优先，否则按新账号配置/健康计划回退，不扩大真实上游调用上限。
- [x] 流式最终失败/取消不建立成功记忆；HTTP 成功但实际渠道不明或不一致时仍可记住本次指定渠道，却不能在任何统计/日志里声称实际命中或缓存命中；并发晚完成、身份/配置/账号变更不得错误归属或泄露。
- [x] 默认开启、成功后滑动有效期 60 分钟且重启清空；有明确会话标识的同 owner/模型请求能按记忆优先；仅消息开头相同而无明确 ID 的独立对话不共享新增渠道偏好。普通日志与管理投影只有有限来源/命中事实，不保存会话原值、指纹及任意正文；所有影响路由的结果有聚焦与全量测试。
