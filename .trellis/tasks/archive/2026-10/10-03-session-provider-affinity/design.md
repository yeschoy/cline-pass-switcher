# Design: session-scoped Provider preference

> Planning draft, not permission to implement. Source study: parent `research/upstream-pinning-comparison.md` and `.trellis/spec/backend/quality-guidelines.md`.

## Boundary and ordering

Keep `handleChat()`'s sequence: authenticate/owner → resolve model/identity → select and lease account → resolve that account's complete route → build Provider plan → perform Provider attempts. This feature changes **only the order of eligible named attempts** inside `runChatChain()`, never account selection, upstream credentials, quota/RPM admission, static exclusions, durable Provider hard quarantine/cooldown, `retryRules`, or SSE replay rules.

A session hint is `(owner-scoped HMAC identity, resolved model) → last successful *attempted* Provider slug`. It is **not** evidence of actual Provider, pin acceptance, or cache use. Make it a bounded process-local extension of the existing `sessionBindings` owner (`server.js:1330-1447`), not a second high-cardinality binding table. Existing account binding must still work when its pipeline/workflow flag is on; Provider hints must also work when account binding is off. This requires typed/optional subrecords or equivalent within that same owner, with independent expiry for the two functions and unchanged bounds/invalidation guarantees. Never persist HMAC fingerprints or raw identities; bound per-session model hints and total entries under the existing configurable maximum.

Proposed default: Provider preference enabled, successful use slides its TTL to 60 minutes, process restart drops it. No new affinity for `message_hmac`/no identity; retain the current `extractSessionIdentity()` explicit Codex/Claude/generic parent priority, and owner namespace introduced in `handleChat()`. The incoming `prompt_cache_key` forwarding/derivation remains unchanged. A narrow persisted administrator opt-out of Provider preference is the rollback switch. Show it as a native toggle in the existing model/routing settings, with a server-validated config field; it must not be coupled to the account-pipeline `sticky` flag or assembled from incomplete account rows.

## Request and settlement

1. Snapshot the preference before the first real attempt after selecting/ leasing an account. Consult it only when identity confidence is `explicit`, the hint model matches the resolved model, and its slug remains in that account's currently eligible candidate list (including its complete per-account route). A hint that is excluded, cooling, hard-quarantined or held by scheduled probing loses priority for this request; it never revives a banned channel. If the first attempt is already fixed by source order, promote the hint ahead of `strict` and `preferred`; after any failure use the existing remaining-candidate health order and `maxRetries`, excluding attempted providers. If a new account is allowed by the existing pre-stream replacement path, rebuild its plan and recheck the same session hint against **the new account's** complete route.
2. Record a hint only on the **terminal successful** named attempt of a successful request. Non-stream: after the final chain status/response is known; stream: only from its one terminal finalizer when the accepted stream completes successfully, not when the first data event merely commits headers. `auto` has no named slug. Failure, recognized SSE error, transport error, local RPM rejection and cancellation never establish a new hint. Do not copy Go's early-stream `observeStick()` behavior.
3. Use a request-local sequence/generation to prevent an older concurrent turn completing late from replacing a newer successful preference; a failed newer turn cannot erase a still valid earlier success merely by starting. Successful updates carry the **attempted slug** even if `routing.finalProvider` is unknown or mismatches it, per user's A choice. Preserve the actual/mismatch fact independently; label diagnostics `session-target-preferred` and `planned-only`, never `actual-hit` or `cache-hit`.
4. On model/owner changes and explicit identity validation failure, never cross-match. On account key/proxy/owner rotation, use the current account binding invalidation path but do not transfer owner credentials; a Provider preference is revalidated against the new route at each selection. If a scheduled per-account hold is released before the 60-minute hint expires, the old hint may become eligible again; otherwise it expires without a raw-session trace.

## API / persistence / projection

The smallest candidate is a top-level `sessionProviderAffinityEnabled: true` config flag for an operator rollback switch, with strict management validation and old full-save omission preservation. No durable Provider hint or extra storage file. The UI switch uses the existing `api()` and owning snapshot/generation, not a complete object rebuilt from visible cells. Log only a bounded selection enum (`session-preferred` versus existing strict/health), and perhaps a boolean `sessionProviderPreferenceApplied`; do not output fingerprint, session value, list of bindings, or another inferred actual Provider. Keep existing target/actual/usage fields separate.

## Compatibility / rollback / tests

With no explicit identity, `auto`, an ineligible hint or feature disabled, existing candidate order is byte-equivalent. Disable the feature to immediately restore old ordering without deleting static route config. Restart clears only process-local hints, not config/account state. Migration must not overwrite invalid operator JSON. Local mock tests: strict and preferred modes; parent/child identity; no-ID message collision; different owner/model; account route override and pre-stream replacement; excluded/cooling/hard or scheduled-held hint; maxRetries 0; SSE success/error/cancel; actual unknown/mismatch still remembering planned slug without fabricated hit; concurrent completions; TTL/eviction/restart; no leaked identity in logs/API. Run the full project gate and real browser if a toggle is exposed.
