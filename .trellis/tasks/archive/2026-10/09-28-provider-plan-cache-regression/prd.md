# 核查供应商计划与缓存命中率变化

## Goal

解释截图中长供应商列表的含义，核实该请求的实际 Provider 尝试数；首先比较用户新截图所标的两个独立对话各次请求的缓存 Token 表现及路由，再判断整体缓存指标是否下降、与近期变更有无可证实关联。

## Background / Confirmed facts

- 第一张截图中 2026-09-28 17:12:30（界面本地时间）的请求为 `200 / success`，显示 sticky / cache-pool-active、回退绑定命中及缓存命中；长列表包含 15 个候选 Provider。截图自身无法显示实际尝试次数或总体命中率。
- 用户补充的第二张截图用两个红框标出两个独立对话：上框数次请求缓存 Token 量明显低于下框；其中 17:12:30 的上框请求显示缓存约 128 Token，但第一张截图将其标为“缓存命中”。这并不矛盾：Switcher 的 `cacheHit` 只要求明确的 cachedTokens > 0，不衡量命中量的高低。两个截图来自不同界面，其缓存/输入 Token 计量是否完全同口径尚待核实；不能仅凭图像断定缓存机制失效。
- `public/index.html:1799` 的供应商列优先显示 `targetProviders`，实际 HTTP 尝试在请求记录 `attempts` 中；`server.js:3794-3821,4491,2892-2930` 将计划和 trace 分开投影。`test/integration.test.js:3336-3352` 验证计划候选可以多于实际尝试。
- `cacheHitRequestRate = cacheHitRequests / cacheKnownRequests`，其中缓存字段缺失是未知而不是未命中；缓存 Token 占比是另一个指标（`server.js:2581-2582,2828,4410-4412`）。单行缓存命中不能说明整体趋势。
- 最近一次有证据的生产发布为 `a17eef6`，容器于 2026-09-27 20:32:00 UTC 启动；发布时仍是 sticky、缓存池最小 5，未启用 `load-health`（`.trellis/tasks/archive/2026-09/09-17-deploy-cache-pool-validation/research/version-boundary-20260927-load-health-code.md`）。本地 `git merge-base --is-ancestor 378ff1f a17eef6` 已验证：`378ff1f` 是该发布提交的祖先，不是之后的本地业务变更；仍必须实时复核运行版本、重启及配置边界。
- `/api/statistics.recent24h` 是持久化的滚动分钟桶，不是发布后窗口；上次 2026-09-27 只读复核已指出混合版本和策略的窗口不能用于验收（`.trellis/spec/backend/deployment-guidelines.md`、`.trellis/tasks/archive/2026-09/09-17-deploy-cache-pool-validation/research/read-only-recheck-20260927.md`）。
- 此任务与现存的 `09-28-pool-concurrency-benchmark` 独立；不得触发或复用其付费压测流程。

## Requirements

- 仅对现有代码、提交/发布记录与获授权的生产**只读**安全投影做分析。不得发送付费聊天、修改配置/服务/数据、清空日志、开启详细采集或访问/导出请求正文、密钥及私有完整 JSON。
- 先确定生产实际 release/image、启动时间、账号模式、缓存池关键设置及其变更时间；不能验证的字段标记未知，不用本地 HEAD 冒充生产代码。
- 以截图所示请求 ID 定位一条普通请求日志（若保留且可访问），区分候选数量、`attempts` 的 Switcher 尝试 trace 数、最终 Provider、账号切换、缓存命中与亲和事实；trace 不代表网关内部重试，个别 `req.end()` 前同步失败也可能记入 trace，不能无条件当作到达远端的调用数。再按两框的时间序列核对各自的实际账号/Provider、尝试数、绑定/亲和/上游键、用量口径与缓存 Token 变化；Switcher 普通行不保存逐请求 cachedTokens 数量，须从原计量界面的安全投影取得。只报告安全聚合/必要的非敏感诊断字段，不传播账号名称、原始日志或标识符，也不读取对话正文。
- 区分“是否有任何缓存”（boolean 命中率）与“缓存了多少 Token”（缓存 Token 数量/可比的输入 Token 比例），优先解释同一对话内逐次变化、两个对话之间的差异；不能以缓存命中率高代替缓存量高。
- 在个案核对后，再选取尽可能可比的发布/配置边界前后窗口，分别给出已知缓存样本数、命中请求数/率、未知占比、可比时的缓存 Token 占比及实际多尝试比例；注明模型、owner/池、流式、账号分布/流量混合与观察时长差异。比较窗口若不可连续归属，明确“证据不足”。
- 将代码路径变化、模式/路由/账号配置和观察到的尝试/绑定漂移分别列为已证实事实或假设；不从时间相关性直接推断因果。已归档历史报告只作时间边界/方法线索，不代替当前观测。
- 不进行自动回滚或修复；如提出调整建议，列出所需额外证据和风险，等待单独授权。

- [ ] 给出当前生产版本/策略的证据及可信时间边界，或逐项标出无法验证的状态。

- [ ] 区分缓存请求命中率、逐请求缓存 Token 量、Token 占比、亲和/绑定和 Provider 重试，给出有证据等级的原因排序及后续建议。
- [ ] 报告只含安全聚合，不包含生产凭据、配置原文、正文、账号身份或完整原始日志；未经批准不更改生产或业务代码。
