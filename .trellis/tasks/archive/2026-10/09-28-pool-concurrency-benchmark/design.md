# Design — bounded live-pool capacity measurement

## Boundary and trade-offs

This is a production **account import followed by measurement**, not a release. First add the three operator-specified upstream accounts through an existing authenticated administrator console session. The full-list account save must preserve every existing account and global mode, active selection, pool target, health/retry rules, routes, diagnostic settings and runtime environment. Do not start an isolated switcher/mock or otherwise adjust scheduling to improve the benchmark. Reuse the current deployment and one explicitly identified client-key owner pool. A 350 requests/minute **aggregate generator ceiling** is not an account-level limit and does not establish the service maximum when no knee is observed.

Use only non-secret aggregates from authorized management projections and container telemetry. An authenticated account-list response includes private keys, notes, headers and proxies: never dump it to stdout, artifacts, fixtures or the model context. If access is available, filter inside the private execution context to counts/dispositions/caps by owner, discarding the raw response before any output. Similarly, keep the client credential confined to a private execution context (not CLI arguments, command output, source files, Git or request logs); do not use a default repository config or copy DATA_DIR. If no safe credential path exists, stop and ask the operator rather than bypass authentication. Protect concurrent background traffic: it consumes capacity and RPM, so observed results are conditional on load at the measured window.

## Measurement shape (proposed, subject to review)

Add only the three named accounts, use their supplied upstream keys without echoing them, note `09-28下午`, match the latest comparable Legacy account settings (enabled, maxConcurrent 7, maxRpm 0, weight 1, priority 100, no proxy/custom Headers/account route). Save once; re-read three entries and unchanged existing count/configuration. Do not restart the service or manually overwrite `DATA_DIR`. An unexpected diff or failed save stops the benchmark for operator recovery; never blindly restore a concurrent save.
1. Preflight read-only **after import**: exact running release/version, service health, selected owner pool's non-secret eligible/active/standby counts, finite/unlimited account caps and current RPM availability; route and real model compatibility. Validate that the test entry is the intended production ingress; do not accidentally bypass a TLS/proxy path while claiming end-to-end performance. Do not expose account names/IDs or secrets. If the owner pool, model or safe authorization cannot be established, stop.
2. The first selected model (`cline-pass/glm-5.3-flash`) failed its one-request dry-run with two upstream HTTP 500 attempts and is excluded from RPM inference. The operator explicitly selected `cline-pass/deepseek-v4.1-flash` as the second fixed workload; freeze a new boundary and repeat all model-specific preflight. Set a fixed, minimal benign prompt, bounded output-token setting, no retries at the client and distinct session identities so sticky scheduling does not collapse the test onto one account. Identify stream and non-stream as different tests; first pass uses non-stream unless the real workload requires SSE. Verify the selected model's route with one request and account/attempt/header behavior without retaining response bodies.
3. Two axes: a paced offered-rate staircase below and up to 350 requests/minute, and separate adaptive simultaneous-request bursts (for example 1, 2, 4, 8, ...) until the first attributable admission failure or health guard. **No preselected result peak**: the approved 64-in-flight emergency safety cap prevents unbounded production impact and is labelled a censoring limit if reached. Limit the **total** requests and wall time across both axes; do not infer concurrency from generator worker count. Count in-flight from admission/telemetry and observed overlapping upstream attempts when possible. Rate windows shorter than 60 seconds cannot establish a 60-second rolling RPM cap; require at least two continuous minute windows at the final rate for a sustained claim, with an explicit warmup and UTC attribution boundary.
4. Collect only aggregate offered/accepted/succeeded rates, client p50/p95/p99 (sample caveat), timeouts and error categories, local 429 (`blockedBy`/zero attempts) versus upstream 429/5xx, peak observed in-flight, safe server CPU/RSS/event-loop evidence if available, and baseline/control traffic. An HTTP 200 with an error payload must not be counted as useful success; completed RPS including local 429 must not be called successful RPS.
5. Stop on predefined rolling error/latency/resource guards, auth drift, the first *observed* provider retry fanout, downstream-visible 429, persisted quota protection, or evidence that background traffic is being harmed. The service may retry an internal upstream 429 before exposing a result; this host-only observer cannot stop at the internal event instant. Treat this as an explicit approval gate, not as a proven immediate safety property. Close/cancel remaining client requests safely and do not perform automatic recoveries. Preserve only non-secret aggregate research artifacts and a bounded decision log; no production diagnostic bodies or operator state.

## Diagnostic branch after the two failed dry-runs

At the time of the two-request diagnosis, retain the original capacity runner unchanged as a separate mode. In the existing host-only Python source and no-echo stdin/SSH wrapper, add an explicit alias-aware preflight: `pc/deepseek-v4.1-flash` must map **exactly** to approved `cline-pass/deepseek-v4.1-flash`, the resolved target must be known, not chained, and each eligible Legacy account's **resolved** complete route must have integer `maxRetries <= 1`. The diagnostic never substitutes a different owner/key or bypasses the public ingress. The previous `max_tokens=8` workload is not evidence of a provider saturation knee; archived 16→256 empty-response observations concern different requests, so do not assert the current 500 cause.

After independently reviewed preflight, an explicit diagnostic mode alone can send a non-stream request with `max_tokens=256`, then only on useful single-attempt success one SSE request with exactly the same alias, prompt and cap. Hard bounds: two sequential downstream sends; four potential attempts reserved per send (eight total); one in-flight; 120-second wall budget with five seconds for drain; 350-per-rolling-minute ceiling still applies. Client does not retry. On the first observable 429, fanout, health/protection/auth/config drift, malformed response, timeout or cancellation stop; no ramp. Incremental SSE parsing has bounded line/event/total bytes, rejects an error event/envelope, requires non-whitespace content delta and `[DONE]` plus clean EOF; no content/reason is printed, logged or persisted. The fixed whitelist output classifies modes and attempts but is not request-attributed provider telemetry. Server-internal 429/provisional protection can precede detection and paid work may outlive an SSH break. A two-request success says only that this minimal workload worked on this occasion, not that 8 was causal or that the pool sustains any RPM.

## Subsequent local-only streamed capacity revision

After the separately documented successful diagnostic, revise **only the capacity mode** to use the exact client alias `pc/deepseek-v4.1-flash`, resolved target `cline-pass/deepseek-v4.1-flash`, `stream: true` and `max_tokens: 256` for dry-run, paced steps and bursts. The same alias/target/no-chain/resolved complete-route preflight now gates capacity preflight and execution. Keep the two-request diagnostic mode independent and keep the original 350 rolling RPM, 900 downstream/observed-or-reserved attempts, 300s and 64-client-in-flight emergency envelope. Reuse the bounded SSE reader; useful success requires one observed attempt, meaningful delta, `[DONE]`, no SSE error and clean EOF. Count success-only end-to-end stream latencies and report unresolved sends distinctly; stage RPS is a stage-span quotient, not a steady-state rate. These changes are locally testable only, **not** a live capacity run or authorization for one. Before any paid ramp, obtain a fresh alias-bound key/health/route preflight and independent operator approval for the revised all-stream workload. No result from the earlier direct-model 8-token runs or the narrow comparison is a measured concurrency/RPM threshold.

## Decision and validity

A threshold is the highest **observed** rate/concurrency meeting the approved error and latency guardrails across the test window for this model, owner pool, time and external background load. If 350 RPM or the emergency concurrency ceiling passes without a knee, report `>= highest tested`, never an absolute maximum; if it fails, report the observed pass/fail interval and stop the production run at the first 429 as approved. Account finite sum is at most a conditional local upper bound for the selected active set; any unlimited cap removes a finite numeric bound, and different owners cannot be pooled into one client's capability. A rate limit may consume more than one attempt per chat under provider retries; measure real attempts rather than equating them with requests. No recommendation to change production limits follows automatically from a measurement.

## Rollback / risk

The approved import is the only intended persisted mutation. On unexpected live effects, stop generation immediately and record safe aggregate status for operator follow-up; never automatically rotate keys, recover accounts, edit configuration or restart the service. Temporary benchmark process/state should be enumerated and cleanup proposed after user consent; Trellis logs are retained.
