# Bounded live-pool generator — review required before any live run

This is a **request generator, not a safe preflight or a capacity verdict**. Do not run against production until the main operator independently confirms the exact HTTPS ingress, running release, explicitly authorized client-key owner, compatible low-cost model, account eligibility/RPM headroom, background traffic, diagnostic state and a private credential handoff. No repository config, DATA_DIR, account list or key file is read by this program. It never performs management calls. The task's approved envelope is global, **not a per-account limit**. Main agent handles live preflight/monitor and independently reviews this code; no production run is part of local verification.

## Private invocation contract

Supply an approved **client** credential as exactly one nonempty line on inherited read-only fd 3; the private broker must close the writing end after supplying it. It must not appear in argv, environment, shell history, source, output, or a committed file. Supply a separate, independently authenticated **read-only aggregate health monitor** on inherited fd 4; it sends one JSON line `{"ok":true}` at least every 5 seconds, starting before traffic, only while health, account protection/cooldown, owner/credential binding, external traffic and CPU/RSS/loop/ingress guards remain acceptable. It sends `{"ok":false}` and closes on any drift; SIGINT/SIGTERM is the manual emergency brake. Neither descriptor is printed; a missing, false, malformed, oversized or >6s stale heartbeat fails closed. This monitor is an **external prerequisite**; generator does not itself observe server CPU, account protection, owner identity or real upstream in-flight attempts. If such a monitor or private fd broker cannot be provisioned safely, **do not run**. Do not substitute static `ok:true` for the live monitor. No automatic recovery, configuration edit or service restart is performed.

After those gates and independent review, the private supervisor launches the child with these arguments (placeholders only; keep the URL/model out of reports if private):

```text
node .trellis/tasks/09-28-pool-concurrency-benchmark/research/live-pool-generator.mjs \
  --origin=https://<approved-ingress> --model=<approved-model> \
  --execute --preflight-confirmed
# supervisor attaches private key pipe at fd3, safe heartbeat pipe at fd4
```

Only the exact `/v1/chat/completions` route is used; no redirects, retries or GET catalog calls. Public targets must be HTTPS origins with no userinfo/path/query/fragment. `--local-test-only` permits only HTTP(S) loopback and must never be used for production. There is no default URL or credential. The program does not verify that the supplied key actually belongs to the preflight owner: the supervisor must verify and continuously watch that mapping **before** authorizing the launch. A client key alone cannot access the authenticated management projections.

## Workload and interlocks

Non-stream Chat Completions, fixed prompt `Reply OK.`, `max_tokens: 8`, unique random `session_id` per request, one dry run requiring one observed upstream attempt and a nonempty useful choice. Dry run → paced 60/120/240 RPM (six seconds each, subject to dropped ticks and at most ~42 offers) → paced 350 RPM for 120 seconds if budget/headroom allows → separate adaptive bursts 1/2/4/8/16/32/64 **subject to the same sliding 60s limit**. Each step waits for previous work to drain, and stops at the first guard; successful bursts do not imply server lease count equals requested burst size. There is no predetermined concurrency peak: 64 is an **emergency ceiling/censoring limit**, never a claim of measured service capacity. The final 120s window must be checked for full coverage before any sustained-RPM claim; shorter/dropped windows are short-window evidence only. Concurrent background traffic is not controlled.

Hard ceilings across **all** steps: at most 350 offered in every rolling 60 seconds, 900 offers total, 64 outstanding client requests, and a five-minute wall envelope (generation ends at 298s, allowing up to one second of abort/drain). Responses have a 30s timeout and 64KiB processing bound; a bad status is classified at headers and its body is discarded. First 429 of any origin stops immediately; 503/protection-like unavailable, auth/owner drift, malformed or error-bearing 200, unexpected multiple attempts, first network failure, oversized reply or unsafe monitor also stop. Two 5xx/timeouts in the rolling last 20, <95% useful successes in a complete last 20, or rolling p95 >2× first successful baseline **and** >10s also stop. The first successful sample is a weak baseline: independent operator guardrails can be stricter. An external monitor is responsible for live CPU/memory/loop/health/background/protection aborts. On stop, outstanding sockets are destroyed; previously sent work can still incur upstream charges. No test retries occur, but **server provider retries may occur**; `X-Cline-Attempts` is checked and any observed fanout stops.

## Output and validity

One JSON aggregate to stdout: stop reason, sent count, per-step offered/completed/useful successes, rates over measured step wall time (including drain), nearest-rank p50/p95/p99 **only on useful successes**, attempts sum/known count, local-zero-attempt/attempted/unknown 429, other bounded error counts, and peak **client-side** in-flight (not proven server leases). It intentionally emits no URL, model, credential, response body, request id, session id, account id/name or upstream slug. Stderr setup failures are generic. A missing `X-Cline-Attempts` is unknown rather than zero; a 429 with no reliable attempt header is `unknown429`. A positive attempt count on a 429 is `attempted429`, **not** proof of upstream 429: a failed real attempt followed by local retry-RPM rejection also has positive attempts. Classify local vs actual upstream 429 only from separately authorized safe request-log aggregates with status/attempt attribution; never infer it from this header alone. CPU/RSS/event-loop, account state and unrelated traffic must be recorded separately as safe aggregates with exact UTC attribution; without these, there is **no production capacity verdict**. The generated JSON itself is task research evidence, not a raw production log; review it before retaining. No output files are created by the generator. The separate process/broker/monitor and any operator-created temporary files must be inventoried and cleaned only after consent; Trellis logs stay.

## Purely local verification

`node --test .trellis/tasks/09-28-pool-concurrency-benchmark/research/live-pool-generator.test.mjs` uses only an in-process loopback mock and synthetic key via anonymous fd; it exercises stop-on-429, 200 error envelope and watcher veto. It does not prove two sustained production minutes, production upstream success, server leases, proxy topology, or a live capacity threshold.
