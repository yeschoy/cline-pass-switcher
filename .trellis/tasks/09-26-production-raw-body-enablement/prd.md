# Production enablement of raw detailed bodies

## Goal

Plan a safe, reversible release that gives administrators failed-attempt detail or all eligible request detail, with unredacted **bodies** only after a separate raw opt-in. Show safe request/response Header names and values without ever storing sensitive Header values verbatim. The prior mixed sanitized-full/raw-error proposal is superseded. The operator approved local code-candidate implementation after plan review; this does not authorize a release, production resource change or raw capture.

## Confirmed baseline (read-only, 2026-09-25)

- Production release `20260924-173240-32a150e3-diagnostics` is running/healthy, restart 0 and no OOM, under a **536,870,912-byte (512 MiB)** cgroup limit; its `CLINE_PASS_RAW_BODY_READY=1` flag is absent. Private config projection: `detailedLogging=true`, `errorDetailLogging=true`, `rawBodyLogging=false`. The server requires the explicit readiness flag **and detected >=2 GiB** merely to make raw mode available. Raising the limit alone is not proof that multiple 35 MiB bodies and slow administration reads are safe.
- The published code supports **35 MiB per raw body**, a **512 MiB shared retained reservation** with a 64 MiB sanitized-subset fence, 48h raw retention and existing 1 GiB combined store cap. Raw body bytes can contain secrets or private messages; Headers, list metadata, ordinary JSONL and configuration are not authorized to expose them. Existing admin Cookie/CSRF/transport controls deny client keys management.
- A prior target-like 512 MiB synthetic raw-body load produced OOM, so direct setting activation on the current container is blocked by both the resource gate and absent readiness flag. Old-image rollback must isolate former client-key management ingress and the private raw directory; ordinary backups must omit raw groups or enforce an independent private 48h deletion policy. The 2026-09-24 code-release record remains `awaiting-admin-acceptance`, with an opaque current config hash different from its recorded immediate migration hash. Do not silently mark it accepted or overwrite later operator saves.
- Local `main`/`origin/main` have been pushed to `9aaa691`, but production still runs `32a150e`. Pushing is **not** deployment; rolling out `main` would also migrate client-key ownership and has an independently documented unsafe old-image-on-v2 rollback path. Do not conflate that change with raw enablement.

## Requirements

1. Error-detail selects real failed upstream attempts (including a failed attempt before eventual success); full-detail selects all eligible request/response content. Both may be on, with full taking precedence and only one group. Keep `rawBodyLogging` independent and default-off, plus administrator initialization and explicit runtime readiness/memory admission; without raw opt-in, legacy sanitized behavior persists. Once raw is enabled, full retains ingress/attempt/downstream bodies and safe request/response Header projections, while error-only retains failed-attempt request/response bodies and safe Headers. The running implementation omits raw Header values and cannot satisfy this by toggling settings. Show only bounded safe Header names and independently safe/redacted values, **never** verbatim Authorization/Cookie/upstream-key/Set-Cookie or arbitrary credential-bearing values in manifests, lists, ordinary logs or backups. Preserve body/budget/48h limits, fail-open model traffic and independent administrator access.
2. Prepare a reversible **new committed code candidate** for safe Header projection: the deployed implementation cannot satisfy it by settings alone. The operator chose the normal committed-`main` release path for planning; this explicitly includes already-pushed pricing and multi-key changes and requires complete private pre-upgrade backup, schema migration rehearsal, account-owner isolation, and safe old-image rollback. Local code-candidate implementation is approved; deployment and production raw enablement are not. No unapproved account/routing configuration changes. Keep live raw mode false through candidate tests, migration rehearsal and pre-admission gates.
3. On an isolated copy under the proposed target cgroup/hardening, run concurrent <=35 MiB request/SSE/slow-admin-download conditions and measure RSS, event-loop delay, OOM/restarts, capture resource drops and chat parity. A 512 MiB reservation is not an RSS upper bound. Stop on failed budgets or unexpected credential projection; don't weaken safety fences.
4. Before writing any raw production body: independently verify root-private raw backup exclusion **or** a hard private 48h backup expiry, old-image management ingress isolation and raw-manifest/body denial on copied state, 48h store expiry/recovery, and a tested exact-image/config rollback. A service TTL cannot erase external backup copies.
5. Require administrator-only real-browser verification of one-time risk warnings, explicit choice, on-demand raw body read, navigation/session clear, keyboard/focus/narrow width and no client-key access. Use synthetic fixture data for body contents; don't copy/print production raw body or credentials. Maintain normal log/Header/metadata exclusions.
6. Only after all gates pass and operator approves the reviewed live cutover: enable raw mode through its authenticated persist-first management endpoint, verify the accepted setting, data retention and model-traffic health, retain rollback materials and a bounded monitoring window. If any gate fails, keep raw off and report the blocker. Never turn on raw capture through a direct config edit or misrepresent an HTTP 401 as authenticated acceptance.
7. Resolve the older code-release acceptance separately: attribute the user's actual protected-page check as operator testimony and compare only safe changed field paths against an identified private rehearsal/backup before accepting the current config hash. No automatic `deployment.json` completion from a generic assent or unmatched hash.

## Remaining review gate

The candidate image and measured memory limit cannot be chosen before isolated tests. After code and resource/backup/rollback/browser gates, present the exact live cutover for separate operator approval. Raw-group exclusion from ordinary backups is the default; if it cannot be proved, stop rather than inventing an external-expiry owner.

## Out of scope

Production paid-model load, per-client-key quotas, relaxing ordinary-log or configuration privacy, automatic retention of raw backups beyond 48h, or retroactively recovering previously omitted diagnostic bodies. Pushed pricing/multi-key code is included only in the release *plan*, not yet authorized for deployment.
