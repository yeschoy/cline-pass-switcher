# Code-only raw-off cutover: fresh v1 snapshot and fenced rollback analysis (2026-09-27)

**Scope:** read-only design analysis, not a deployment instruction or approval. No production SSH, service mutation, raw enablement, backup promotion or authenticated production request was performed for this note. Research is based on repository specs and previously recorded, bounded rehearsals; the proposed combined cutover/rollback remains untested. The older September 24 release acceptance and production raw-body admission are separate pending gates.

## Evidence and the stale snapshot question

- The authorized **backup-only** window paused the exact old container, sealed a root-private, raw-excluded non-raw `DATA_DIR` tree (2,355 entries, 91,046,345 bytes), backed up Compose/env/gateway/deployment sidecars, then unpaused the **same** old container. A separate full-copy restore booted old v1; a different copy migrated all 32 stable accounts to `legacy` under the candidate. The stage deliberately remains `trusted:false` and is *point-in-time*: writes resumed. See `research/production-backup-window-20260927.md`.
- The final committed-`main` candidate is source `4d4ee8798f20a03e842d5cd52f21188bd1f0f88a`, Compose-built image `sha256:bd49772e0a42a2f4f90bc35ce32408485d411caca46efe40c4b13c959105669d`; isolated full-copy startup passed at 512 MiB with raw off and no readiness flag. On **that snapshot**, v1 config `0cb45b6d…` migrated to `e56819de…`, adding only `clientKeys` and 32 `accounts[].clientKeyId=legacy`; metadata quota attempt fields changed nondeterministically. At last recorded observation, old image `sha256:0bd1deaefb04b6c2c3f1e3417eddc07b3fc6dd6398212ff98e6a783c3c62100c` remained healthy. Recheck all identities and hashes at any future window; release parent is UID-1000-owned and source files/image need a fresh integrity gate. See `research/raw-off-release-candidate-20260927.md` and `research/post-save-migration-20260927.md`.
- **Conclusion:** matching only the old `config.json` SHA-256 after resumed operation permits *at most* treating its **config-specific migration prediction** as a hypothesis, subject to a fresh current config/metadata copied-data rehearsal with the same exact candidate image and startup conditions; it does **not** make that backup a current **complete rollback**. `metadata.json`, statistics, quotas, logs and detailed groups may have gained bytes even when config did not change; restoring the old tree would erase legitimate intervening traffic and administrative evidence. A separate *post-upgrade v2* copy protects current data from destruction but is not a compatible old-image input and cannot automatically replay v2-only state into v1. The old image is proven unsafe on v2 (`.trellis/spec/backend/client-key-guidelines.md`, Upgrade / rollback gate). Do not promote the old stage by flipping `trusted`, mixing stale v1 config with current metadata/logs, or taking a config-only backup. A stale restore with acknowledged data loss would be a different, explicitly authorized disaster-recovery decision, not the minimal normal rollback.

## Minimal proposed single write-fenced code-switch window

This is **one newly reviewed interruption**, not a reuse of the earlier backup-only 10-minute authorization. A combined copy/switch window reduces the otherwise inevitable gap between an old-service unpause and a later deployment backup. Retain both images and all private stages; `data/detailed-logs/raw/` is excluded from ordinary backup and remains separately inaccessible, never silently discarded. No generic backup framework or new scheduler is needed; reuse the measured inventory/rsync/seal approach **only for backup verification**, not as a deployment/rollback orchestrator (`research/backup_pause_window.py` explicitly forbids deploy/restore).

1. **Before any live-service mutation:** obtain a separate approval for the exact raw-off code-only sheet, interruption bound and operator/external-writer fence. Confirm authoritatively all writers of `DATA_DIR` and Compose/env/gateway/deployment sidecars; an FD sample or a promise alone does not prove absence of scheduled writers. Freeze administrator/config/account writes and establish a model-ingress/in-flight-drain policy; pause blocks but does not finish open streams and is not a full external-writer fence. Verify current old container ID/image/health/restarts/OOM/512 MiB, raw=false, no ready flag, committed `main == origin/main`, archived source/modes, candidate Compose **exact built image** and private integrity, live paths/mounts, hashes, admin state, gateway loaded configuration, disk and helpers. Rehearse atomic replacement/restore on **private scratch**; prove pre-mutation failure leaves live Compose/data/image/container unchanged. Have independent admin positive-check capability ready; do not expose secrets. If any gate drifts, abort before interruption; repeat the copied-data migration rehearsal on current config **and** metadata even when config still matches `0cb45b6d…`, then freeze the fresh config prediction. Metadata hash is an observation, not a deterministic startup-migration target. See `.trellis/spec/backend/deployment-guidelines.md` and `research/raw-off-release-candidate-20260927.md`.
2. **Under a continuously enforced write fence:** quiesce/finish native traffic and prevent new ingress; ensure no other host/external writer can create, remove or change files. **Prefer the simpler reviewed stop-and-copy sequence**: after every preparatory gate has passed, stop only the exact old container and verify its process is stopped, cannot auto-restart and has no replacement writer; this is the first deliberate service-mutation/outage boundary. Do not rely on the backup-only pause/watchdog procedure for this combined window. Resync the **entire current non-raw v1 tree** into a fresh root-owned 0700 stage, plus authoritative Compose, env, resolved gateway and deployment sidecars. Verify framed relative paths, bytes, uid/gid, modes, entry count and source → copy → source parity, raw exclusion, old config SHA and per-sidecar SHA, then rehearse an independently restored full v1 copy **without writing to the live tree**. A stopped exact-ID restore must be rehearsed separately: on failure before Compose installation, start **the same** old container on its unchanged v1 tree/Compose, verify ID/image/health/local route and reopen ingress only after recovery; the backup-only pause watchdog does not supervise a stop/start. No acceptance until the chosen method has a bounded rehearsal and independent outage recovery. If no uninterrupted writer fence or time reserve remains, restore only the old service using its original Compose (unpause the exact ID only if the alternate pause method was expressly reviewed), prove health and abort; never advance to migration on an unverified backup.
3. **Close the backup-to-Compose gap explicitly:** with the recommended stop-and-copy, leave the old container stopped and all ingress/other writers fenced from the final source scan **through** Compose install and new-image startup; do not restart it between copy and `up`. Test exact stopped-old → candidate `docker compose up -d --no-build` behavior on disposable Compose, including container identity, name conflict, restart policy, failed-up recovery and bounded outage. The old image can write metadata/logs asynchronously while running (`server.js` startup normalization, quota/diagnostic/statistic saves); matching config alone cannot excuse any unpause/restart gap. An alternate pause method must be **separately reviewed/rehearsed**: the existing watchdog can unpause the old ID at its deadline and must not stay armed through v2 startup, potentially creating two writers. Transfer its ownership to a tested cutover supervisor, unpause/stop under a continued external write fence, and prove old cannot write before new mounts `DATA_DIR`. Never run Compose against an ambiguous paused container; if that ordering is not provable, use the stopped method or stop the release. The backup helper was designed to unpause/recover the **same** container and is not a cutover tool; see `research/backup-watchdog-preflight-20260927.md` and `research/production-backup-window-20260927.md`.
4. **Switch only after the current v1 backup is sealed and old writer fenced:** atomically install a candidate Compose differing only by image tag/build context; start via `docker compose ... up -d --no-build` (never rebuild). Keep unchanged gateway/env, 512 MiB, no readiness flag and raw=false. Record the exact live-mutation boundary (including any stop/pause of old service); failures earlier are a proved no-op **to the running old service**, while failure after quiescence requires active recovery. Confirm newly running image ID, source hashes, UID 1000 mode, Docker running/healthy, zero restarts/OOM, bounded startup errors, local `/api/meta` and predicted config hash *immediately* after migration; compare 32 ordered stable account IDs and safe non-owner field paths, all `legacy`, empty additional-key inventory and raw=false. Do not pin a metadata hash: compare only allowed safe schema paths, preserve the live metadata bytes; a later quota timer may update them. Any unexpected config change stops acceptance and requires write-fenced investigation, not automatic overwrite. See `.trellis/spec/backend/database-guidelines.md`, `.trellis/spec/backend/client-key-guidelines.md` and `.trellis/spec/backend/deployment-guidelines.md`.
5. **Independent ingress and administrator gates:** under the reviewed route policy check localhost, actual public HTTPS hostname/gateway attestation, and `ai-internal` model alias/availability without exposing keys or sending paid traffic. Require real independently authenticated Cookie/CSRF `/api/models`, `/api/statistics`, request logs and detailed settings reads, bounded bad quota-refresh input rejection, and client-key-only management denial; 401 only proves negative denial, not positive administrator access. Compare gateway active configuration/Host/Origin and replaced proxy Headers; old-image rollback must deny management from **public, host loopback as appropriate, and internal network peers**, not merely one Nginx path, while preserving approved model availability. If operator-only protected pages are outstanding, label testimony and `awaiting-admin-acceptance` plainly; a hard authenticated route failure with available admin access requires rollback. Check admin-auth file remains independent and unchanged. Actual browser focus/raw acceptance and >=2 GiB load are **not** part of this raw-off code switch (`.trellis/spec/backend/admin-auth-guidelines.md`, `.trellis/spec/backend/deployment-guidelines.md`).

## Fenced rollback / abort states

- **Preparation or backup failure before old pause/stop/Compose/data mutation:** preserve untrusted stage; verify old Compose/config/data identity and *same healthy old container*, with no stop-first rollback. A failed already-paused backup is not pre-mutation: recover/unpause that exact old container and wait for health, retain independent watchdog until unambiguous recovery. If deadline fires or coordinator disappears, watchdog only provides best-effort recovery; do not claim guaranteed availability.
- **After v2 startup or any migration but before new writes can be excluded:** close ingress, wait for/terminate in-flight work under a declared policy and independently exclude background writers; otherwise preserve current bytes and stop for a recovery decision. With writers fenced, seal a **separate complete root-private post-upgrade v2 copy** (including compatible sidecars, preserving operator changes and v2-only account/history state) before any v1 replacement. Verify hashes/inventory and prove current v1 seal and exact old image still exist. A one-file `config.json` rollback while v2 is running is unsafe. Restore the **fresh full compatible v1** `DATA_DIR` (non-raw tree) and its appropriate old Compose/env/gateway/admin sidecars atomically/fail-closed, verify parity and original config/metadata/admin bytes **before** starting exact old image. Old image never starts against writable v2. A config equality to `e56819de…` is only one fence; for the whole-tree restore require independently checked no intervening data/sidecar writes or explicit acknowledged preservation/loss handling. If v2 data has drifted, first preserve it and obtain a fenced recovery decision; don't overwrite a later operator save. Test same-image no-op, wrong-hash abort, mid-restore failure, old v1 boot/health and v2 preservation on isolated full copies before authorization.
- **Ingress security on old-image fallback:** the exact rollback target `32a150e` already has independent administrator authentication: a current production loopback gateway probe with the effective Legacy client key and an isolated restored-v1 probe rejected client-key-only management with 401. This is **negative-only** evidence, not proof of positive administrator login or public/internal-peer isolation. The deployment guide warns about earlier shared-key rollback images; the observed `32a150e` denial narrows only this exact image and these tested routes, not the public/internal or positive-admin gate. The prior raw-manifest denial rehearsal used an **earlier** `274755…` image, not rollback target `0bd1…`; `32a150e` itself supports raw profiles. Raw is off and the current raw child empty for this code-only candidate, but any later raw-on rollback must explicitly isolate the raw child and test denial under the exact old image/gateway. Complete ingress rollback acceptance remains unproved. Fence public and internal management access **before** old start/traffic recovery, maintain raw child isolation (do not traverse/copy it), verify an authorized model path remains and both client-key-only management and raw manifest/body attempts fail from each reachable network path. If isolation cannot preserve the model route, treat old-image rollback as blocked and preserve v2/hold ingress rather than start a permissive old image. See `research/isolated-preflight-20260926.md`, `.trellis/spec/backend/client-key-guidelines.md`, `.trellis/spec/backend/admin-auth-guidelines.md`.
- **State after machine gate:** record the running commit/image and `awaiting-admin-acceptance` atomically with machine versus operator evidence; *healthy means deployed*, not accepted. Later config/metadata/log drift is normal but may make rollback a lossy recovery; preserve old/v2 private copies, compare only safe changed paths, ask intent before accepting a different config hash or restoring. The older `32a150e` deployment record remains an independent acceptance transaction. Do not automatically set any release `completed` from a generic assent or HTTP 401.

## Explicit review/authorization boundary and unresolved proof

Present a **new combined backup-and-raw-off code-switch sheet** with the exact current old/new IDs, hashes, writer/ingress and traffic-drain fence, fresh full v1 and separate v2-copy handling, isolated restore/rollback tests, pause-watchdog handoff or rehearsed stop-first recovery, maximum outage/recovery threshold, gateway/internal admin denial checks and failure triggers. Obtain **separate operator approval before any production pause/stop/Compose/data/ingress mutation**; prior backup-only approval cannot be reused. If any dependency (writer fence, chosen stop/restart recovery or alternate pause-to-switch handoff, old-image management ingress isolation, current full-backup test, admin verification strategy) is unresolved, recommend no live switch. Do not combine this approval with raw-ready/memory changes or `/api/logs/settings` raw=true; those need their own >=2 GiB/resource/backup/browser gates and later reviewed authorization (`.trellis/tasks/09-26-production-raw-body-enablement/{prd,design,implement}.md`).

It does not provide the missing independently supervised stop/start recovery or live ingress/authentication gate.
