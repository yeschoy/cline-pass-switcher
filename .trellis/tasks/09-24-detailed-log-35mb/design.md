# Production raw-body diagnostics — planning draft, security-sensitive

## Explicit product exception and hard dependency

The operator has authorized **production persistence and remote admin viewing of unredacted request/response bodies**, up to 48h, to reduce body sanitizer work. This does not authorize raw Headers, account configuration values, ordinary JSONL, model client diagnostic responses or secret-bearing list metadata. The body itself may contain secrets and private conversations: this is unavoidable and must be warned about rather than falsely called sanitized. The completed/archived `09-24-separate-console-login` task satisfies the prerequisite: client API keys are denied management, the administrator completed the first change and the no-bootstrap restart was accepted. This grants local implementation of the separate default-off feature, **not** production enablement. Raw mode is a new explicit default-off choice; an existing enabled `detailedLogging` setting or an older sanitized manifest cannot silently opt into raw.

## Owners and limits

Keep `DetailRoot`/`BodyCapture` as the single observation owner and `DetailedLogStore` as the only publication/retention owner. Cap: 35 MiB per body, 512 MiB shared retained-payload reservation; treat both as **diagnostic** limits, not outbound traffic/RSS caps. Keep legacy sanitized captures at 5 MiB per body and their existing sanitizer work/output bounds; do not raise them to 35 MiB just because raw mode is supported. Reserve before copying with bounded per-root/account activity and pending publication; do not assume 512 MiB reservation implies <=512 MiB heap/RSS. Re-examine multiple bodies (ingress, upstream attempt input/output, downstream), possible duplication, and streaming backpressure. The existing 1 GiB disk cap remains; new raw groups expire within 48h even if capacity remains, sanitized legacy groups keep seven days. Raw manifests use a **different profile identity** (`raw-full` / `raw-error`) from the existing sanitized `full` / `error`. This ensures the previous release's validator refuses every raw group, even under 5 MiB, if an old shared-key image is restored. The new store preserves a safe capture-profile display and marks each descriptor `redacted:false` for raw (sanitized legacy remains true). Never project raw text into list/inventory or accidentally make a raw manifest look like an old sanitized group. Reuse safe same-directory atomic group publication and group-level eviction, same generation/clear fences, no second store or reader that loads all bodies into memory.

Only skip **body** sanitization. Raw mode stores exact valid UTF-8 body bytes up to 35 MiB, with explicit truncation/interruption; an invalid UTF-8 body is omitted, not silently replacement-decoded. Error-only raw capture publishes request/response bodies of **failed attempts only**, never successful attempts. Header values and free-form list/manifest metadata are omitted in raw mode unless independently safe without scanning the body; fixed method/path/status/UUID/profile and bounded ID facts may be retained. Never copy configured account keys or downstream Authorization proactively. Sanitized legacy mode keeps its existing group-wide discovery and protection; ordinary JSONL/metadata/service errors do not change. Ordinary JSONL remains a strictly bounded projection. Preserve existing sanitized old groups and the error-only profile's failed-attempt selection. Diagnostic failure is fail-open for chat; auth and management setting persistence are fail-closed.

## Retrieval, retention, and deployment

Raw body API requires the existing independent admin session and same-origin transport gate, no-store/nosniff and bounded on-demand retrieval rather than eager inventory content. Browser warnings distinguish explicit raw risk and clear loaded raw body text on selection, navigation, logout and session loss; no `innerHTML` interpolation or persistent browser storage. Directory/file modes stay 0700/0600; ordinary service output contains no raw body. The **same DetailedLogStore** owns both legacy sanitized UUID groups in its existing root and raw groups under a private `raw/` child (not a second store, queue or retention owner). Raw group directory names include an immutable bounded creation timestamp and UUID; a strict basename plus only regular allowlisted body/manifest files and no symlinks establishes service ownership independently of manifest parsing. Validate the manifest timestamp against the directory timestamp when it is readable. Reads reject raw groups at 48h; at startup and minute maintenance, delete these demonstrably owned expired raw groups **even if the manifest is corrupt**. Physical deletion is best effort while the process is running and storage writable, with failures surfaced in safe health and retried; no exact-to-the-millisecond disk erasure claim. A suspicious/unknown entry cannot be served or automatically deleted; report it for manual review. The same aggregate 1 GiB accounting, inventory bounds, serial queue, generation and clear gate apply across both roots; seven-day legacy groups keep their existing behavior. No disk TTL can remove external copies. External backups/copies are outside the store TTL: before any separately authorized production raw enablement, the deployment backup procedure must exclude raw groups or apply a separately enforced private 48h backup expiry. Old shared-key releases neither traverse the `raw/` child nor accept the new raw manifest profile; management ingress must also stay isolated on rollback. Rehearse that exact combination privately before a production switch. No raw mode is enabled or deployed in this task.

## Resolved implementation bounds / remaining verification

- Display exact **35 MiB per raw body / 512 MiB shared retained reservation**, with 5 MiB sanitized mode unchanged. Budget admission occurs before copying; serial publication and UI retrieval must remain bounded. This is not an exact RSS guarantee; measure peak memory with multiple local fake 35 MiB bodies and record the observed bound before claiming operational readiness.
- Invalid UTF-8 raw body: explicit omission with preserved traffic, not replacement characters or a binary download. Truncated valid UTF-8 prefix retains a labelled incomplete descriptor.
- The 48h owned-raw TTL includes corrupt manifests with verifiable ownership; unknown/suspicious entries remain inaccessible, undeleted and discoverably warned for manual remediation. A production rollout needs a separately authorized private copied-data backup exclusion/rollback rehearsal.
