    实测结论（决定了本工具的工作方式）：

    ① 上游可枚举、可观测：订阅模型响应元数据里带背后真正的模型 ID、可用上游列表与本次实际命中的上游；
    「探测」按钮还会用一次零 token 消耗的假上游请求让网关报出精确的可用上游清单（直连→OpenRouter，规划器→Vercel AI Gateway）。

    ② 两类管道都能精确钉住上游（已实测 finalProvider 随之改变）：
    直连管道（OpenRouter）用顶层 provider.only；
    规划器管道（Vercel AI Gateway）必须用 providerOptions.gateway.only——
    switcher 的每次 HTTP attempt 只注入一个 provider，避免网关内部不可观测的多渠道 order 回退。
    两类管道还都支持 sort（最低成本 / 最快首字 / 最高吞吐）。

    ③ 目录模型 :free 变体：属于直连管道，可精确钉住。

    ④ 多上游优先级 + 健康故障转移：switcher 严格按人工顺序逐次发送单 provider 请求，只临时绕过仍在冷却的渠道，不按健康标签重排其余渠道；全部冷却时仅放行最早恢复者。流式请求在首包（SSE 开始）前同样可切换，SSE 开始后只更新未来健康状态、绝不重放。
